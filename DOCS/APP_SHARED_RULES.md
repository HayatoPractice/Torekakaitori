## 7. インシデント管理（参照推奨）

→ **詳細手順は `CLAUDE.md` 起動シーケンス STEP 3 を正本として参照すること。**

各プロジェクトの CLAUDE.md が一元管理している。本ファイルはその存在を周知するためのポインタ。

> **インシデント管理の正しい解釈：**
> インシデントは「必ず守るべき絶対ルール」ではなく、「過去に起きた問題への注意喚起」です。
> 「以前このような問題があったので気をつけてほしい」という参考情報として作成されています。
> AIは過去の経験を踏まえた上で、現在の状況に応じて判断してください。

要約：
- **起動時・類似機能を作る前**：インシデント管理フォルダの `_PRE_CHECKLIST.md` と `INCIDENT_INDEX.md` を参照（注意喚起として）
- **機能追加・編集・削除のたびに**：INCIDENT_INDEX.md で関連タグを照合し、過去の経験として参考にする
- **不具合解決後**：§7-2 の手順でユーザーへ確認してから記録（セッション終了まで持ち越さない）
- **目的**：過去の失敗を参考情報として活かし、同様の問題を未然に防ぐ

### 7-1. 記録より検査を優先する（最優先ルール）  ← INC-055

**記録しただけでは再発は防げない。実際に、記録済みのインシデントが3件再発している（INC-016・026・030）。**

インシデントは54件・16万字、事前チェックリストは117項目・約20分ある。
**人もAIも、毎回の作業前にこれを読むことはできない。**

| いつ | やること |
|---|---|
| **起動時・作業前** | 文書を読む前に **`npm run guard` を実行**する。落ちたらそれが最優先の作業 |
| **インシデント記録時** | 「機械が検査できる形に落とせるか」を**必ず自問**する |
| 落とせる場合 | **その場で** `scripts/guard.mjs` の `CHECKS` に1件足す（後回し禁止） |
| 落とせない場合 | そのときだけ `_PRE_CHECKLIST.md` に書く |

**目安：「同じ間違いをコードで表現できるか」。できるなら検査にできる。**

検査を書くときの4原則：
1. **`why`（なぜ困るか）を必ず書く** — 無いと、検査を消して通す人が出る
2. **例外は理由つきで明示する** — 黙って除外すると、次の人が同じ判断をできない
3. **違反箇所をファイル名で指す** — 探させない。直せる形で出す
4. **足したら、その場で「わざと壊して」捕まえることを確かめる**（INC-058。後回し禁止）
   — 「名前が文字列として存在するか」ではなく「実際に使われているか」を見ること。
   実績：書き下ろした12件の検査のうち3件は、確かめるまで働いていないことに気づけなかった
   （import が残っているだけで合格・別ファイルに名前が残っていれば合格・引用符違いで無反応、の3パターン）。

導入していないアプリは `scripts/guard.template.mjs` と `scripts/guard-selftest.template.sh` を
コピーして使う。**コピーしたら必ず `SRC`（guard側）と壊し方の対象パス（selftest側）を
そのアプリの実際のソースに合わせること**
（ずれたままだと1件も検査せずに全項目が合格し、最も危険な状態になる。雛形側で検知して止まる）。

### 7-2. 記録前にユーザーへ確認する

開発中に不具合・問題・重大な事故のようなものが発生したら、インシデントファイルへ**記録する前に**、
必ずユーザーへ一言確認する。無断で記録しない・記録しないまま済ませない、の両方を避けること。

**確認フォーマット（簡潔でよい）：**
```
【インシデント記録の確認】
何が起きたか：[1〜2文]
記録してよいですか？（Yes / No / 内容を修正してから記録）
```

- Yes → `_TEMPLATE.md` を使って記録し、`INCIDENT_INDEX.md`（一覧・タグ表・カテゴリ統計）と
  `_PRE_CHECKLIST.md` を更新する。「機械が検査できる形に落とせるか」も併せて自問する（§7-1）
- No / 記録不要と判断された → 記録せず、理由を一言添えて完了報告する
- 明らかに軽微な修正（タイポ等）で確認するまでもない場合は、この限りではない

### 7-3. 類似機能を作るときは、着手前に必ず過去事例を確認する

「前と似たようなものを作る」場面が、実は最も再発しやすい（IME入力・認証・キャッシュ・
バックアップ対象漏れなど、同種のミスが複数回記録されているカテゴリがある）。

- 新機能・類似機能の実装に着手する**前**に、`INCIDENT_INDEX.md` の「技術スタック別クイック検索」で
  関連タグを必ず照合する（§7 起動時ルールの再掲ではなく、着手のたびに毎回行う）
- 類似事例が見つかったら「⚠️ 参考：過去に類似の問題がありました [INC-XXX]」とユーザーに共有してから実装する
- 実装後は `npm run guard`（存在する場合）を通し、既存の検査に抵触しないか確認する（§7-1）

### ▌ C. コード修正開始フロー（skeletonizer.py の強制）

1. **全体像の把握**: まずディレクトリ構造を確認する。
2. **構造の抽出**: 編集対象や依存関係にあるファイルについて、生ファイルを読む前に **必ず** 以下のコマンドを実行して構造（シグネチャ）のみを確認する。
   `python3 scripts/skeletonizer.py <対象ファイル>`
3. **生ファイルの読み込み**: 編集対象が確定し、詳細なロジックが必要な場合のみ、生ファイルを読み込む。
4. **実装・修正**: 該当箇所を修正する。

## 8. コード修正・ファイル編集時の必須注意事項（修正を行う全タイミングで適用）

**このルールはバグ修正・機能追加・ドキュメント更新のいずれにも適用する。**

### 8-1. 修正前チェック（着手前に必ず実施）

1. **影響範囲の特定**：`scripts/find_impact.py` を用いて、修正対象ファイルや関数が他ファイルから参照されているか確認する
   ```bash
   python3 scripts/find_impact.py <対象ファイル名または関数名>
   ```
2. **クロスファイル副作用チェック（6視点）**：
   - 視点①：同じ変数名・関数名・セクション名を他のファイルが参照していないか
   - 視点②：修正によってドキュメント間の「参照先」が存在しなくなっていないか
   - 視点③：スクリプトファイルを修正する場合、呼び出し元スクリプトへの影響がないか
   - 視点④：DOCS_INDEX.md のタスク別早見表からのリンクが壊れないか
   - 視点⑤：sync_to_apps.py の同期対象リストに影響がないか（新規ファイル追加時）
   - 視点⑥：CLAUDE.md や AGENTS.md から参照されているセクション名を変えていないか

### 8-2. スクリプト修正時の追加ルール

- `sync_to_apps.py`：修正後は必ず `--dry-run` モードで動作確認する
  ```bash
  python3 scripts/sync_to_apps.py --dry-run
  ```
- `post-merge` / `install_hooks.sh`：修正後は必ず `scripts/check_code.sh` で全自動静的検証（構文チェック）を実行する
  ```bash
  bash scripts/check_code.sh
  ```
- `setup_auto_sync.sh`：このファイルは **廃止済み（launchd方式）** のため、原則として修正・実行しない

### 8-3. ドキュメント修正時の追加ルール

- **セクション名の変更は連鎖修正が必要**：`## セクション名` を変更すると、他のMDファイルが参照している可能性がある
  - 変更前に `grep -r "旧セクション名" DOCS/` で全参照を確認してから変更する
- **CLAUDE.md の `## セクション名` 変更は `sync_to_apps.py` の `STANDARD_CLAUDE_SECTIONS` 変更も必要**
  - 変更後は `sync_to_apps.py` の L48-55 も合わせて更新すること

### 8-4. セッション終了時チェックリスト（毎回確認）

セッション終了前に以下を確認する：
- [ ] 新しいアプリ種別・ライブラリ・ツールを採用した場合 → `CROSS_REFERENCE.md` §1 に追記する
- [ ] 新しいパターンを発見した場合 → `CROSS_REFERENCE.md` §5 に追記する

- [ ] `MINUTES.md` を最新の状態に更新する

## 9. 学習ログのローテーションルール

学習ログが **500行を超えた場合**、以下の手順でローテーションする：

1. `DOCS/LEARNING_LOG_ARCHIVE.md` を作成（なければ新規）
2. 最も古い記録を `LEARNING_LOG_ARCHIVE.md` の末尾に移動する
3. アーカイブ済みの記録は `MASTER_LESSONS.md` への昇格が済んでいるか確認する

> ローテーション基準：500行 / 理由：AIのコンテキスト読込コスト最小化

## 10. 実装前宣言ルール（コード着手前に必ず実行）

**このルールは全てのコード生成・ファイル編集に適用する。**

### 10-1. 実装前宣言（着手前に必ず宣言してから着手する）

コードを書く前に、以下を必ず宣言する（省略禁止）：

```
【実装前宣言】
- 何を作るか：[機能・コンポーネント名]
- なぜこの設計か：[選んだ理由・代替案との比較]
- 影響範囲：[変更するファイル・影響を受けるファイル]
- 懸念点：[潜在的なリスク・未確定事項]
```

この宣言が曖昧な場合は、着手前に社長に確認を求める。

### 10-2. 思考停止デフォルト禁止ルール

**「理由なくデフォルト値を使うこと」は禁止する。**

禁止される判断例：
- 「とりあえずblue-500」「なんとなくInter」「なんとなくSuapabase」
- 「前のプロジェクトで使ったから」という理由だけで選ぶ
- 理由を言語化できない技術選択

許可される判断例：
- 「このプロジェクトはダッシュボード系なのでMUIが最適」（理由あり）
- 「ユーザーが青系でと指定したのでblue-600を使う」（ユーザー指定優先）
- 「前プロジェクトで実績があり、今回も同条件なのでSupabaseを選ぶ」（理由あり）

**ユーザーが明示的に指定した内容は、このルールより常に優先される。**

### 10-3. 二重指示の禁止（新ルール追加時に必ず確認）

新しいルール・チェックリストを DOCS ファイルに追加する前に、「AIが指示なしで既に行うこと」でないか確認する。
該当する場合はルール化しない（トークン浪費・二重指示による過剰修正の原因になるため）。
書いてよいのは、**このプロジェクト固有の判断・禁止事項・数値基準・フォーマット**のみ。
判断に迷う場合は付録A（AIツール別・自動化差分表）を確認する。

## 11. ユーザー指示の安定性保証

このプロジェクトの方向性・ルール・設計方針は、ユーザー（社長）が長期間かけて構築したものである。

- **AIは勝手に方向転換を提案しない**：「〇〇に変えた方がいい」は、ユーザーが質問した時のみ回答する
- **決定済みの技術スタックに疑問を呈しない**：承認済みの技術選択に毎回コメントしない
- **ユーザーの指示が変わったと感じたら確認する**：自己判断で方針変更しない。「以前の指示と異なりますが、変更しますか？」と確認する
- **このルールブック（各DOCSファイル）に記載された内容は、ユーザーが意図を持って決定したもの**として尊重する

## 14. 修正サイクル義務（コード1行でも省略禁止）

> いつ・誰が・どのAIを使ってバイブコーディングしても、コードを修正する際は必ず以下のサイクルを完走すること。「コードを直した」だけでは未完了。「検証まで完了した」時点で初めて完了とみなす。

```
① 修正する

② 修正後のコードを論理的にトレースして検証する
   - 副作用が出ていないか（他ファイルへの影響）
   - 意図通りに動くか（ロジックを手で追う）
   - TypeScript型エラー・importエラーがないか
   - 既存機能へのリグレッションがないか

③ 問題が見つかれば修正して②に戻る
   （問題が解消されるまでこのループを繰り返す）

④ 問題がなくなったらビルドコマンドを実行し、
   エラーなく完了したことを確認してから完了報告する
```

### 14-1. 論理トレース（②）で必ず確認すること

| チェック項目 | 確認内容 |
|:---|:---|
| **副作用** | 変更した関数名・変数名・型を他のファイルが参照していないか |
| **型安全** | `npx tsc --noEmit` で TypeScript 型エラーがないか |
| **リグレッション** | 修正箇所に依存する既存機能が壊れていないか |
| **ビルドエラー** | import 解決エラー・未使用変数のエラーがないか |
| **ドキュメント整合** | 変更内容と `.md` ファイルの記述が乖離していないか |

### 14-2. ビルドコマンドの選択

| 技術スタック | ビルドコマンド |
|:---|:---|
| React + Vite | `npm run build` |
| Next.js | `npm run build` |
| TypeScript 型チェックのみ | `npx tsc --noEmit` |
| GAS（Google Apps Script）| ビルド不要 → ブラウザ確認 |

### 14-3. スキップが許容されるケース

**④ビルド** のみスキップ可：
- コメントの追加・修正のみ
- `.md` ドキュメントのみの変更
- 設定値の軽微な変更（ロジック変更を伴わないもの）

**② 論理トレースは一切省略禁止。** いかなる場合も必ず実施すること。

### 14-4. After Gate（インシデント記録）

④ビルド完了・完了報告の直後に必ず実行する（§7 インシデント管理と連動）。

```
今回の修正で新しい問題・パターンが発生した → _TEMPLATE.md からファイル作成 → INCIDENT_INDEX.md 更新
発生しなかった                            → 完了報告のみ
```

## 15. Backtracking プロトコル（行き詰まり時の必須対応）

> 同一課題で3回以上失敗した場合、即座に作業を中断してアプローチを変更せよ。「同じ穴に4回落ちること」は禁止。

### 15-1. トリガー条件

以下のいずれかが **3回** 繰り返された場合、Backtracking を発動する：
- 同じエラーが fix しても解消されない
- 異なる修正を試みても別の問題が再発する
- 実装してもテスト・検証が通らない

### 15-2. Backtracking 発動時の手順

```
Step 1: 作業を完全に止める（コードを書き続けない）

Step 2: 現在のアプローチを一言で言語化する
        「今のアプローチ：○○を使って○○する方法」

Step 3: 別アプローチを2〜3案提示する
        「代替案A：○○を使う方法（メリット・デメリット）」
        「代替案B：○○に分割する方法（メリット・デメリット）」

Step 4: 社長（ユーザー）に相談する
        → どのアプローチで再挑戦するかを確認してから再開する
```

### 15-3. 再挑戦前の根本原因チェック

Backtracking 前に以下を必ず確認する：
- [ ] `MASTER_LESSONS.md` の既知の地雷に類似ケースがないか
- [ ] インシデント管理の類似インシデント（INCIDENT_INDEX.md）がないか
- [ ] 前提条件（ライブラリバージョン・環境変数・設定）が間違っていないか
- [ ] 問題を「最小再現コード」に切り出せるか（切り出せると解決が早い）

> **SERVICE_ORG_CORE.md の「fix を3回繰り返しても解消しない → ブロッカー報告」と連動する。**
> 3回目の失敗でアプローチを変える提案を行い、社長の判断を仰ぐこと。

## 19. PDCAサイクル完全実施ルール（全作業場面・絶対遵守）

> **作業開始・途中再開・コード生成・修正・設計のいずれにも無条件で適用する。**

### 19-0. PDCA 全体フロー

```
P（計画）→ D（実行）→ C（確認）→ A（修正）
                          ↑___内部ループ（問題解消まで繰り返す）___↑

↓ 全 TODO タスク完了

  ↓ 問題なし
作業完了
  ↓ 問題あり → 修正（A フェーズ）→ 完了
```

### 19-1. P フェーズ（計画・設計）【省略禁止】

#### 19-1-1. 自動質問ルール（実装着手前に必ず実施）

以下の条件に1つでも該当する場合、コードを書く前にユーザーへ自動的に質問する：

**質問すべき条件：**
- 実装方向が複数あり、どちらにするか判断材料が不足している
- ユーザーの意図・要件が曖昧で方向性が確定できない
- 機能の詳細（UI 挙動・データ設計・エラー時の処理）が未定義
- 追加仕様が当初の目的と矛盾・乖離する可能性がある

**質問しない条件（以下は質問不要）：**
- 当初の目的・機能達成に重要でない細部（フォントサイズの微調整等）
- 明らかに「こうするしかない」パターン（業界標準・セキュリティ必須要件）
- 既に REQUIREMENTS_LOG.md や会話内で合意済みの内容

**質問フォーマット（このフォーマットで質問すること）：**
```
【確認事項】[N]点あります。実装前にご確認をお願いします。

① [質問内容]
   → 現在の想定：[AI が考えている実装方向]
   → 代替案：[あれば]

② [質問内容]
   （同上）
```

#### 19-1-2. P フェーズ 目的逸れ・矛盾チェック（必須）

計画を立てる際に以下を必ず確認し、問題があれば実装前に報告する：

| チェック項目 | 確認内容 |
|:---|:---|
| **目的整合** | 実装内容が当初の目的・ユーザーのゴールに沿っているか |
| **代替案** | 技術的に困難な場合、同じ目的を達成できる別の方法があるか |
| **矛盾チェック** | 既存の機能・ルール・設計と矛盾する点がないか |
| **重複チェック** | 同じ機能が既に別の箇所で実装されていないか |
| **スコープ確認** | 依頼の範囲を超えた変更を行おうとしていないか |

#### 19-1-3. より良い代替案の自動提案ルール（計画・修正・方針決定の全場面で適用）

方針を決める際、**同じ目的を達成できるが明確にメリットが大きい別の方法がある場合**、ユーザーに聞かれる前に自動的に提案する。

**発動条件：**
- 現在の方針より大きなメリット（トークン削減・工数削減・保守性向上など）がある代替案が存在する
- デメリットが許容範囲内、または事前報告で回避できる内容である
- 目的の本質から逸れない（本質を失う代替案は「やめておく」として却下する）

**提案フォーマット（このフォーマットで必ず提示）：**
```
【代替案提案】同じ目的を達成できますが、より効果的な方法があります。

▼ 現在の方針
  [現在想定している方法]

▼ 代替案
  [より良いと判断した方法]

▼ 代替案のメリット
  [定量的・定性的なメリットを列挙]

▼ 代替案のデメリット・注意点
  [デメリットを正直に列挙。隠さない]

▼ デメリットへの対処法（デメリットがある場合のみ・省略禁止）
  [各デメリットに対してどう軽減・回避・補完するかを具体的に提示]
  例）「プロジェクト固有ルールが反映されない」→「/code-review 後に DOCS の観点チェックリストを手動で実施する」

→ 代替案を採用しますか？（Yes / No / 現在の方針で進める）
```

**判断基準：**

| 状況 | 対応 |
|:---|:---|
| 代替案のメリットが大きい（例：トークン1/10削減） | 上記フォーマットで提案する |
| 代替案が「本質」を失う（UIチェックをコマンドで代替できないなど） | 提案せず現行方針で進む |
| 代替案が存在しない / 差が誤差レベル | 提案しない |

> **例）** 手動での説明文 → `/code-review` コマンドで代替。メリット：構造的・多角的レビュー、トークン削減。デメリット：プロジェクト固有ルールは反映されないため、DOCS の観点チェックは別途必要。

---

#### 19-1-4. TODO リスト作成（P フェーズ完了時・必須）

P フェーズが固まったら「誰が・いつ・どの AI が使っても理解できる」TODO リストを作成し、
`MINUTES.md` の「次のタスク」セクション、または プロジェクトルートの `TODO.md` に保存する。

**TODO リスト フォーマット：**
```markdown
## 【プロジェクト名 / 機能名】TODO リスト
作成日：YYYY-MM-DD ｜ 最終更新：YYYY-MM-DD

### 目的・背景
（このリストで達成したいこと・ユーザーの意図・機能の概要を詳細に記載する）

### タスク一覧（実装順）
- [ ] **[タスク名]**
  - 内容：[何を・なぜ・どう実装するか]
  - 対象ファイル：[ファイルパス]
  - 受入条件：[何が動いていれば完了とみなすか]
- [ ] **[タスク名]**
  （同上）

### 完了タスク
- [x] **[タスク名]**：[完了内容・確認方法]

### 変更履歴
- YYYY-MM-DD：[変更内容]
```

**TODO リスト 更新ルール（重要）：**

| 操作 | 方法 |
|:---|:---|
| ✅ 完了 | `- [ ]` → `- [x]` に変更する |
| ➕ 追加 | 適切な位置に新規項目を挿入する |
| ❌ 削除 | **削除しない**。`~~打ち消し線~~` で表示し、後ろに `→ [削除理由と日付]` を付ける |

> **削除を「消す」のではなく「線を引く」理由：** バイブコーディング中に計画変更の経緯・考え方が後から追える。別の AI や別のセッションで「なぜこれをやめたか」が一目で分かる。

削除例：
```markdown
- ~~[ ] **招待メール機能**：メール招待を実装する → 初期リリース対象外に変更（YYYY-MM-DD）~~
```

### 19-2. D フェーズ（実行）

- TODO リストの **1タスクずつ** 完了させてからチェックを入れる（複数を並行して曖昧な状態にしない）
- §10（実装前宣言ルール）を守りながら実装する
- タスク完了のたびに TODO リストのチェックを更新する
- タスク完了のたびに MINUTES.md のタスクログを追記する（§21 参照）
- **タスクの「完了」= コードが動く + MINUTES.md に記録した時点**（記録なしは未完了扱い）

### 19-3. C フェーズ（確認）

実装後に以下を順番に確認する：

```
Step 1: TypeScript 型チェック — npx tsc --noEmit でエラーがないか
Step 2: ビルド確認 — npm run build が通るか
Step 3: 機能確認 — 実装内容が TODO の受入条件を満たすか
Step 4: 副作用確認 — 他のファイル・コンポーネント・機能に影響が出ていないか
Step 5: UI/UX確認 — モバイル（375px）・タブレット（768px）・デスクトップ（1024px）
                     全画面幅で表示・操作が正常に動作するか
Step 6: ドキュメント乖離確認 — コードと .md ファイルの内容がズレていないか
        （MINUTES.md・REQUIREMENTS_LOG.md が実態と一致しているか）
Step 7: レガシー確認 — 削除忘れのコード・使われていない関数・古いコメントが残っていないか
        grep -r "TODO\|FIXME\|HACK\|XXX\|console\.log" . --include="*.ts" --include="*.tsx"
```

### 19-4. A フェーズ（修正）【内部 C→A ループを含む】

#### 19-4-1. 修正着手前の影響チェック（コードを書く前に必ず実施・省略禁止）

```
Step 1: 修正対象のファイル名・関数名・変数名・型名を grep で検索し
        どこから参照されているかを全て把握する
        grep -r "対象名" . --include="*.ts" --include="*.tsx" --include="*.md"

Step 2: 副作用が出るファイル・コンポーネントをリストアップする

Step 3: 副作用ごとのケア方法を決める
        → ケア可能：同じタイミングで修正する（同一コミットに含める）
        → どうしても弊害が出る：ユーザーに事前報告して了承を得てから実施する

Step 4: 本来の目的・機能から逸れていないか確認する
        逸れている場合：代替案を提示してユーザーの確認を取る
```

#### 19-4-2. 修正実施 → 内部 C→A ループ

```
修正実施（副作用ケアを同時に実施する）
    ↓
論理トレース（§14-1 のチェック項目を全て確認）
    ↓
  問題なし → ビルド確認 → TODO チェック → 次タスクへ
    ↓
  問題あり → 新たな原因を特定する
               ↓
             修正着手前の影響チェックを再実施（Step 1〜4）
               ↓
             修正実施 → 論理トレース → ...繰り返す
               ↓
             3回失敗 → §15（Backtracking プロトコル）を発動する
```

### 19-5. 全体再確認パス（全 TODO 完了後・1回のみ必須）

**トリガー：** TODO リストの全タスクに `[x]` が入った時点で自動的に開始する。

一通りの作業が完了したら「最初から全体を1回だけ見直す」。

```
【全体再確認パスの手順】

Step 1: 今回変更した全ファイルのコードレビュー
  □ 型エラー・未処理例外がないか（npx tsc --noEmit）
  □ 不要なコメント・console.log・仮の TODO コメントが残っていないか
  □ ハードコーディングされた値・シークレットがないか
  □ エラーハンドリングが適切か（空データ・通信エラー・権限エラー）

Step 2: UI/UX 全画面幅チェック
  □ モバイル（375px〜）でレイアウトが崩れていないか
  □ タブレット（768px〜）で問題ないか
  □ デスクトップ（1024px〜）で問題ないか
  □ 全ブレークポイントでインタラクション（クリック・入力・スクロール）が正常か

Step 3: 機能整合チェック
  □ 全タスクの受入条件を満たしているか
  □ 既存機能へのリグレッションがないか
  □ TODO リストの削除済み（打ち消し線）項目が誤って実装されていないか
```

**再確認パスで問題が見つかった場合：**
→ §19-4（A フェーズ）の手順で修正する
→ この修正が完了した時点を **「作業完了」** とする（2回目のパスは行わない）

**再確認パスで問題が見つからなかった場合：**
→ その時点を **「作業完了」** とする

### 19-6. 途中再開時のルール

セッションが途切れて再開する場合：

```
Step 1: MINUTES.md を読んで前回の状態を把握する
Step 2: TODO リストを確認して「どこまで完了しているか」を特定する
Step 3: ユーザーに以下のフォーマットで報告する：

【途中再開確認】

次のタスク：[次の未チェックタスク]

## 20. CLIコマンド・スクリプト優先ルール（指示書記述・設計・レビュー全場面）

> **目的：** 作業指示や設計ルールをコードで書ける場面ではコマンドを使い、
> 長文の散文指示によるトークン消費・解釈ブレを減らす。
> ただし「コマンドを使うことで本来の目的から逸れる」場合は使わない。

---

### 20-1. 指示書・DOCS への記述ルール

新しいルールや手順を DOCS ファイルや CLAUDE.md に書くとき：

| 判断基準 | 記述方法 |
|:---|:---|
| コマンド1行で目的を達成できる | コマンドを記載する（長い散文で説明しない） |
| コマンドでは捉えられない「プロジェクト固有の文脈・判断・ニュアンス」がある | 自然言語で記載する（コマンドを無理に入れない） |
| コマンド + 補足が必要 | コマンドを先に書き、補足を1〜2行添える |

> **「コマンドで書く」は強制ではない：**
> このルールの目的は「長い散文を減らしてトークン消費を下げること」。
> **自然言語でも短くまとまっていれば効果は同じ**。コマンド構文を強制するルールではない。
>
> トークン削減の本質は「長さ」：
> - ❌ 悪い例（トークン多）：「AIは変更ファイルを全て読み込み、型エラー・セキュリティ・UI崩れを確認し、問題があれば修正案を提示し、副作用がないことを確認する」
> - ✅ 良い例A（コマンド）：`` `/code-review` を実行する ``
> - ✅ 良い例B（自然言語）：「コードレビュー実施（型・セキュリティ・UI崩れ確認）」
>
> コマンドの追加メリット：解釈ブレがなく、実行が明確。
> 自然言語のメリット：プロジェクト固有の文脈・判断基準を含められる。

> **目的の本質を守る基準：**
> コマンドを使っても「プロジェクト固有のチェック観点・判断基準・文脈」が失われる場合は
> コマンドを優先しない。コマンドは手段であり目的ではない。

---

### 20-2. このプロジェクトで利用可能なコマンド早見表

現在このフォルダで活用できる Claude Code スキル・コマンドの一覧：

| コマンド / スキル | 代替できる作業 | メリット | デメリット（本質を失う場合） |
|:---|:---|:---|:---|
| `/code-review` | §19-5 全体再確認パス Step 1「コードレビュー」 | 構造的・多角的レビュー / トークン削減 | DOCS の固有ルール・UIチェックは反映されない → Step 2, 3 は別途手動で行う |
| `/security-review` | §16 品質バジェット「セキュリティチェック（OWASP）」 | 網羅的・セキュリティ特化 | 一般的なOWASPチェックのみ / プロジェクト固有の認証設計は別確認が必要 |
| `/simplify` | A フェーズのコード整理・リファクタリング | 簡潔化・重複排除 | バグ修正は行わない / 目的を確認してから使う |
| `/verify` | UI/UX 確認（実際にブラウザで動作チェック） | ブラウザ実環境で確認できる | アプリが起動している必要がある |
| `/fewer-permission-prompts` | settings.json への allowlist 追加作業 | 作業中断が減る | 許可範囲が広がるため、要認識して実施する |
| `/compact` | 長くなった会話のトークン圧縮 | 大幅なコスト削減（最大1/10以下） | 詳細な会話履歴が失われる / デバッグ途中には使わない |
| `/schedule` | 定期タスク・深夜バッチ設定 | 人がいなくても自律実行 | 外部ネット接続・認証が必要な場合は別途設定が必要 |
| `/loop` | 繰り返しチェック・監視作業 | 自動継続 | 条件設定が不明確だと意図しないループが起きる |

**使い方の原則：**
```
1. コマンドで代替できる手順が DOCS にある → コマンドに置き換える
2. コマンドで代替できない「文脈・判断・固有ルール」がある → そのまま散文で残す
3. 一部だけ代替できる → コマンドを先に実行し、残りを手動で補う
```

---

### 20-3. 将来の指示追加時のルール

新しい作業指示・ルールを DOCS に追加する際のチェックリスト：

```
□ この指示はコマンドで達成できるか？
   → Yes：コマンドを記載し「理由（何を補えないか）」を1行添える
   → No：散文で記載し、なぜコマンドで代替できないかを明示しなくてよい
□ コマンドを使うことで「本来の目的・文脈・判断基準」が失われるか？
   → 失われる：コマンドを入れない（本質を守る）
   → 失われない：コマンドを優先する
□ コマンド実行後に「手動補完が必要なステップ」があるか？
   → あれば：その手順をコマンドの直後に明記する
```

## 21. MINUTES.md 議事録管理ルール（全セッション必須）

> **目的：** 新しい AI セッションを開くたびに「これまでの経緯・現在地・次のタスク」を
> 再説明する手間をなくす。MINUTES.md の TL;DR を読めば即座に作業を再開できる。

---

### 21-1. ファイルの場所と管理方針

- **保存先：** 各プロジェクトのルートディレクトリ（`MINUTES.md`）
- **テンプレート（アプリ作成原本）には置かない**（プロジェクト固有ファイル）
- 各プロジェクトで初回セッション時に AI が自動作成する

---

### 21-2. フォーマット（このフォーマット厳守）

```markdown
# MINUTES.md — 作業議事録（AI セッション引き継ぎ用）
最終更新：YYYY-MM-DD HH:MM | セッション #N

---

## ★ TL;DR — 次の AI はここだけ読めば再開できる

| 項目 | 内容 |
|:---|:---|
| 現在地 | [フェーズ・実装中の機能名] |
| 前回完了 | [最後に ✅ になったタスク] |
| 次のタスク | [今すぐ着手すべきタスク（TODO.md の次の項目）] |
| 注意事項 | [次の AI へ必ず伝えるべきこと・地雷・前提条件] |
| アクティブファイル | [現在触っているファイルのパス] |

---

## セッション履歴（新しい順）

### SESSION #N — YYYY-MM-DD HH:MM

#### タスクログ
- `HH:MM` ✅ **[タスク名]** — [何をしたか・結果] `変更: ファイルパス`
- `HH:MM` 🔄 **[タスク名]** — 作業中 → 次セッションへ持ち越し

#### 重要イベント
- `HH:MM` `#決定` **[決定内容]** — 理由：[なぜそうしたか]
- `HH:MM` `#バグ` **[バグの内容]** — 対処：[どう解決したか]
- `HH:MM` `#方針変更` **[変更内容]** — 理由：[なぜ変えたか]
- `HH:MM` `#ブロッカー` **[詰まった内容]** → `#解決` [解決方法]

#### 変更ファイル
[このセッションで変更したファイルの一覧]

---

### SESSION #N-1 — YYYY-MM-DD（要約）
[古いセッションは要約1〜3行に圧縮する]
```

### 21-3. 更新タイミング（必ず守ること）

| タイミング | 更新内容 | 優先度 |
|:---|:---|:---:|
| セッション開始時 | 新しい `SESSION #N` 見出しを追加 | 必須 |
| TODO タスク 1 項目が完了したとき | タスクログに ✅ 追記・TL;DR の「前回完了」「次のタスク」を更新 | 必須 |
| 重要な設計・技術決定をしたとき | 即座に `#決定` エントリを追記 | 即座 |
| バグ・エラーを発見したとき | 即座に `#バグ` エントリを追記（解決後に対処を追記） | 即座 |
| 方針・計画が変わったとき | 即座に `#方針変更` エントリを追記 | 即座 |
| 作業が詰まったとき | `#ブロッカー` を追記（解決時に `#解決` で更新） | 即座 |
| セッション終了時 | TL;DR を最終状態に更新・変更ファイルを記録 | 必須 |

> **❌ 禁止：** 1 返答ごとの追記（ノイズが多く有用情報が埋もれる）

**ログ追記専用ルール（監査ログとして永久保持）：**

| 対象 | ルール |
|:---|:---|
| TL;DR ブロック | 更新可能（常に最新状態を反映する） |
| タスクログ・重要イベント | **追記のみ・削除・編集禁止**（過去の記録は永久保持） |
| 削除したい場合 | ~~打ち消し線~~で表現し削除理由を添える（消してはいけない） |

> **理由：** タスクログは意思決定の監査証跡。削除すると「なぜその判断をしたか」が追えなくなる。

---

### 21-4. タグ一覧（必ずこのリストから選ぶこと）

| タグ | 使い場面 |
|:---|:---|
| `#決定` | 設計・技術選定・UI 方針などの意思決定（BDR 形式で記録 → 下記参照） |
| `#実装` | 機能・コンポーネントの実装完了記録 |
| `#バグ` | バグ発見・エラー発生（解決後に対処を追記） |
| `#方針変更` | 当初の計画から変更があったとき |
| `#ブロッカー` | 作業が詰まったとき（理由も明記） |
| `#解決` | ブロッカー・バグが解決したとき |
| `#設計` | アーキテクチャ・DB・API 設計の決定 |
| `#マイルストーン` | フェーズ完了・リリース・重要な節目の達成 |

**`#決定` エントリのフォーマット（BDR: 意思決定記録）：**

```
- `HH:MM` `#決定` **[決定内容]**
  - 選択肢: [A vs B]
  - 採用: [A]
  - 理由: [なぜ A を選んだか]
  - 影響ファイル: [変更が及ぶファイル名]
```

> BDR を残す理由：別の AI・別のセッションで「なぜこの実装になったか」を説明なしに理解できる。

### 21-5. セッション開始時の動作（必須）

```
Step 1: MINUTES.md が存在するか確認する
  → 存在する：TL;DR を読む（5行で現在地を把握）→ 最新 SESSION のタスクログを読む
  → 存在しない：MINUTES.md を新規作成し SESSION #1 を開始する

Step 2: ユーザーへ再開確認を報告する
  ┌────────────────────────────────────┐
  │ 【再開確認】                        │
  │ 現在地：[TL;DR より]               │
  │ 前回完了：[TL;DR より]             │
  │ 次のタスク：[TL;DR より]           │
  │ ─────────────────────────────────  │
  │ このまま続けますか？               │
  │ または新しい作業がありますか？     │
  └────────────────────────────────────┘

Step 3: MINUTES.md の記述に従い、前回セッションの状態を引き継ぐ
```

### 21-6. 自動圧縮ルール（ファイル肥大化防止）

セッションが **10件を超えた** 場合、または **14日以上前のセッション** は自動圧縮する：

```
1. 古いセッションのタスクログ・重要イベントを MINUTES_ARCHIVE.md に移動する
2. MINUTES.md には最新 5 セッション分のみ残す
3. 古いセッションの残し方：SESSION #N-K — YYYY-MM-DD（要約 1〜3 行）
4. TL;DR は常に MINUTES.md のトップに維持する（移動・削除禁止）
```

### 21-7. SESSION_LOG.md（作業中の詳細ログ）

**MINUTES.md との役割分担：**

| ファイル | 更新タイミング | 粒度 | 目的 |
|:---|:---|:---|:---|
| `MINUTES.md` | セッション終了時 | セッション単位の要約 | 引き継ぎ・再開用 |
| `SESSION_LOG.md` | 作業中リアルタイム | 操作・決定の逐次記録 | 調査・デバッグ・経緯追跡用 |

**SESSION_LOG.md のルール：**
- **追記のみ・削除禁止・上書き禁止**
- コード変更・設計決定・バグ発生のたびに追記する
- `/project:compact` でアーカイブ・圧縮できる（§21-6 同様）

**タグ一覧：**

| タグ | 意味 |
|:---|:---|
| `[CODE]` | コードの実装・変更・削除 |
| `[DESIGN]` | デザイン・UI/UX の決定 |
| `[DECISION]` | 重要な設計判断（後で参照されやすい決定） |
| `[BUG:OPEN]` | バグ発見（未解決） |
| `[BUG:RESOLVED]` | バグ解決 |
| `[NEXT]` | 次セッションへの持ち越し |
| `[MILESTONE]` | 重要な達成点 |

**記述形式：**
```markdown
### HH:MM [タグ] タスク名（1行で何をしたか）
- **実施内容**: 何をしたか（対象ファイルも記載）
- **決定事項**: なぜその方法を選んだか（あれば）
- **次のアクション**: 次にやること
```

**バグ追跡フォーマット（BUG:OPEN と BUG:RESOLVED はペアで記録する）：**

```markdown
### HH:MM [BUG:OPEN] バグ名・現象の1行説明
- **発生箇所**: ファイル名・行番号
- **症状**: 何が起きているか
- **原因（推定）**: 

（解決したら下に追記）

### HH:MM [BUG:RESOLVED] バグ名（上記と同じ名前）
- **解決方法**: 何を変更したか
- **対処ファイル**: 変更したファイル名
- **再発防止**: 同じバグを防ぐために覚えておくこと（あれば）
```

**CHANGELOG.md は不要（SESSION_LOG に統合）：**

CHANGELOG.md は作成しない。SESSION_LOG のタグで同じ目的を達成できる。

| CHANGELOG の目的 | SESSION_LOG での代替 |
|:---|:---|
| 機能追加の記録 | `[CODE]` タグで追記 |
| 重要な設計判断 | `[DECISION]` タグで追記 |
| バグ修正履歴 | `[BUG:OPEN]` + `[BUG:RESOLVED]` のペアで追跡 |
| リリース・マイルストーン | `[MILESTONE]` タグで追記 |

CHANGELOG.md が既存プロジェクトに存在する場合は削除せず無視し、新規記録は SESSION_LOG.md のみに行うこと。

## 22. 修正サイクル完了後のGit pushルール（全作業必須）

> **目的：** 作業ごとに確実にリモートへ保存し、進捗の消失・セッション切断による作業ロストを防ぐ。

### 22-1. pushのタイミング

以下の「作業完了」条件を満たしたら、**即座に** git push を実行する（セッション終了まで持ち越さない）。

| 変更の種類 | push タイミング |
|:---|:---|
| コード変更あり | §14 ステップ④（ビルド確認）完了後 |
| ドキュメント変更のみ | §14 ステップ②（論理トレース）完了後 |
| 設定ファイル変更のみ | §14 ステップ②（論理トレース）完了後 |

### 22-2. 実行手順（省略禁止）

```bash
# Step 1: 現在のフォルダのリモートURLを確認する（必須）
git remote get-url origin

# Step 2: 変更をステージング・コミット
git add <変更ファイル>
git commit -m "<コミットメッセージ>"

# Step 3: 現在のブランチへpush
git push origin HEAD
```

### 22-3. 安全ルール（絶対遵守）

> ⛔ **他のフォルダのリポジトリへの push は絶対禁止**
> push 前に必ず `git remote get-url origin` を実行してURLを目視確認すること。
> 現在の作業フォルダ以外のリポジトリURLへの push は、いかなる理由があっても行わない。
> 誤って別フォルダで作業していた場合はpushせず直ちにユーザーへ報告する。

- **現在の作業フォルダの `git remote get-url origin` で確認したリポジトリにのみ push する**
- 別フォルダのリポジトリURLに push することは絶対禁止
- push 前に必ず `git status` で意図しない変更が含まれていないか確認する
- force push（`--force`）は禁止。コンフリクト時はユーザーに報告する

### 22-4. コミットメッセージ規約

```
<種別>: <日本語で内容を一文>

種別：
  feat   — 新機能追加
  fix    — バグ修正
  docs   — ドキュメント変更のみ
  chore  — 設定・スクリプト変更
  refactor — リファクタリング
```

### 23-1. フォルダ・ファイル構成

```
<各アプリフォルダ>/
└── TODO/
    └── TODO_<作業内容を表す名前>.md   ← 1アプリ1ファイル・独立管理
```

- **1アプリ = 1ファイル**。複数ファイルは作らない
- ファイル名は **作業内容を端的に表す日本語**（例：`TODO_ユーザー認証実装.md`、`TODO_決済機能追加.md`）
- ファイルが存在しない場合、作業開始時にAIが作業内容に合わせた名前で自動作成する
- **各アプリのTODOは独立管理**。原本・他アプリとの連携・同期は行わない
- 原本の `TODO/` フォルダはルール参照・テンプレート置き場として使用する（実作業の手順書は置かない）

---

### 23-2. 手順書作成・追記の動作

ユーザーから「手順書を作って」「手順を追加して」などの指示があった場合：

1. `TODO/` フォルダ内の既存ファイルを確認する
2. 既存ファイルがある → **そのファイルに追記する**（新規ファイルを作らない）
3. 既存ファイルがない → 作業内容に合わせた名前でファイルを新規作成する
4. 新規作業セクションを追加する場合は **§23-7**（日付・見出しの自動挿入）に従う

### 23-3. タスクフォーマット（①②③④⑤⑧⑰）

1タスクの標準フォーマット（全フィールドを活用する）：

```markdown
- [ ] **[手順名]** `[高]` `#カテゴリ`
  - 内容：[何を・なぜ・どう行うか]
  - 対象：[ファイル・コマンド・画面など]
  - 完了条件：[何が確認できれば完了か]
  - 見積：[N分]
  - 依存：[依存するタスク名（なければ省略）]
  - セッション：[SESSION #N]
```

#### ① 優先度ラベル（`[高]` / `[中]` / `[低]`）

| ラベル | 意味 | 目安 |
|:---|:---|:---|
| `[高]` | 今すぐやらないと他が止まる | ブロッカー・本日中必須 |
| `[中]` | 今フェーズ内で完了させる | 通常タスク |
| `[低]` | 余裕があればやる | 改善・後回し可 |

#### ② タスクカテゴリラベル（`#カテゴリ`）

`#UI` `#API` `#DB` `#DOCS` `#テスト` `#設定` などを付与する。
同カテゴリをまとめて着手したい場合に grep で絞り込める。

```bash
grep "#UI" TODO/*.md
```

#### ③ 依存関係の明示

タスクAが完了しないとBが進められない場合：

```markdown
- [ ] **B: レイアウト実装** `[中]` `#UI`
  - 依存：A: APIスキーマ確定
```

#### ④ 工数見積もり / ⑧ 所要時間の実績記録

```markdown
- [ ] **[手順名]** `[中]`
  - 見積：30分

# 完了後（見積 → 実績 の形式で更新する）
- [x] **[手順名]** `[中]` — 完了 YYYY-MM-DD `commit: abc1234`
  - 見積：30分 → 実績：50分
```

> 実績を残す理由：AIの見積もり精度が回を重ねるごとに向上し、計画精度が上がる。

#### ⑤ 担当AIセッション紐付け

タスク追加時に `セッション：SESSION #N` を付記する。
完了時は §23-8（コミットとタスクの紐づけ）に従いコミットハッシュも追記する。

### 23-4. 更新ルール

| 操作 | 方法 |
|:---|:---|
| ✅ 完了 | `- [ ]` → `- [x]` に変更し、完了日・コミットハッシュを末尾に追記する（§23-8参照） |
| ➕ 追加指示 | 既存ステップの適切な位置に差し込む（末尾ではなく文脈に合う位置へ） |
| ❌ 削除指示 | **削除しない**。`~~打ち消し線~~` を付け `→ [理由と日付]` を末尾に追加する |

> **削除を消さない理由：** 「なぜこの手順をやめたか」が後から追える。別のAIや別セッションで二度手間を防ぐ。

---

### 23-5. セッション開始時の動作（⑪⑫）

セッション開始時（§21-5 の MINUTES.md 確認後）に、`TODO/` ファイルが存在する場合は以下を実行する：

```
Step 1: TODO/ フォルダのファイルを確認する
  → ファイルあり：未チェック（- [ ]）のタスクを一覧表示する
  → ファイルなし：スキップ

Step 2: 進捗サマリーを集計する
  完了数 = ファイル内の「- [x]」の件数
  全体数 = 「- [ ]」+「- [x]」の合計件数
  完了率 = 完了数 / 全体数 × 100

Step 3: ユーザーへ報告する
  ┌────────────────────────────────────────┐
  │ 【TODO確認】                            │
  │ 進捗：完了 N / 全 N 件（N%）            │
  │ 未完了タスク：                          │
  │   1. [タスク名] [優先度]               │
  │   2. [タスク名] [優先度]               │
  └────────────────────────────────────────┘
```

### 23-6. セッション終了時の動作（⑮）

セッション終了時（CLAUDE.md セッション終了プロトコル Step 2）に実行する：

```
Step 1: TODO ファイルから未チェック（- [ ]）のタスクを全て抽出する
Step 2: MINUTES.md の TL;DR「次のタスク」欄に未完了タスクリストを転記する
Step 3: セッション終了報告に未完了タスク数を含める
  形式：「未完了TODO：N件（TODO/<ファイル名>.md）」
```

### 23-7. 新規作業セクション追加時の動作（⑥⑬⑭）

#### ⑬ 日付・見出しの自動挿入

この見出しが **マイルストーン（⑥）** の役割も兼ねる。

### 23-8. コミットとタスクの紐づけ（⑤⑲）

§22（修正サイクル完了後のGit push）実行後に以下を行う：

# Step 2: 該当タスクの完了行末に追記する

```

例：
```markdown

### 23-9. ブロッカーセクション（⑨）

- [BLOCKED] **[タスク名]** — 理由：[何が原因で進められないか]
  - 解除条件：[何があれば再開できるか]

```markdown

## 24. アプリ固有設定ゾーン（同期保護ルール）

> **目的：** `sync_to_apps.py` がこのファイルを上書きしても、アプリ固有の追記内容が消えないようにする。

### 24-1. ルール（AIへの指示）

- このファイル（`APP_SHARED_RULES.md`）にアプリ固有のルールを追記する場合、**必ず下記マーカー（`<!-- APP_SPECIFIC_START -->`）より後ろの行に書くこと**
- マーカーより前の行（§1〜§24）は原本から自動同期されるため、ここへの追記は次回同期時に消える
- マーカーは1ファイルに1つだけ存在する。マーカー行自体は削除・移動しないこと

### 24-2. 同期の動作イメージ

```
原本 APP_SHARED_RULES.md      アプリの APP_SHARED_RULES.md（例）
─────────────────────────     ───────────────────────────────────
§1〜§24（共有ルール）          §1〜§24（← 原本で上書き）
<!-- APP_SPECIFIC_START -->    <!-- APP_SPECIFIC_START -->
（テンプレート説明）           ## このアプリ独自ルール   ← 保護される
                               - 何か固有のルール        ← 保護される
```

→ 同期後：原本の §1〜§24 に更新され、マーカー以降のアプリ固有部分はそのまま残る

## 25. バグ調査トリガー（バグ発見・エラー発生時に必ず実行）

> **発動条件：** 以下のいずれかが起きた時点で即座に発動する（スキップ禁止）
> - ユーザーからバグ・不具合の修正依頼があったとき
> - コード実行中にエラーが発生したとき
> - テスト・ビルドが失敗したとき
> - 「動かない」「おかしい」「直して」などの言葉があったとき

### 25-1.（削除済み：世間一般のデバッグ手順 — 2026-07-31）

> **削除理由：** 再現確認・エラーメッセージ精読・直近変更確認（`git log`/`git diff`）・最小再現・
> 仮説列挙・環境確認・依存関係確認は、現代のコーディングAIが指示なしで既に行う標準デバッグ手順であり、
> 明文化は §10-3「二重指示の禁止」に反する。`scripts/hooks/debug_check.py` も同じ理由で
> プロジェクト固有7項目のみに削減済み（詳細は付録A）。

### 25-2. このプロジェクト固有のバグ調査（バグ発見・エラー発生時に実施）

以下のプロジェクト固有の調査を実施する：

```
Step 1: TypeScript 型エラーの確認
  npx tsc --noEmit
  → 型エラーがバグの根本原因になっていないか確認する

Step 2: ビルドエラーの確認
  npm run build
  → 実行時エラーではなくビルド段階で検出できるエラーがないか確認する

Step 3: 影響範囲の把握（§8-1 参照）
  python3 scripts/find_impact.py <バグが発生しているファイル名または関数名>
  → 変更が他のどのファイルに影響しているか確認する

Step 4: ファイル構造の把握
  python3 scripts/skeletonizer.py <対象ファイル>
  → ファイル全体の構造（関数・型・エクスポート）を把握する

Step 5: インシデント管理の参照（§7）
  → INCIDENT_INDEX.md を参照し、過去に同様のバグが記録されていないか確認する
  → 類似事例あり：「⚠️ 参考：過去に類似の問題がありました [INC-XXX]」として共有する

Step 6: MASTER_LESSONS.md の確認
  → 過去セッションで学んだ既知の地雷・パターンに類似ケースがないか確認する

Step 7: §15 Backtracking 発動確認
  → 同じ問題で3回以上失敗した場合、即座に §15 Backtracking プロトコルを発動する
```

### 25-3. バグ解決後の記録（必ず実施）

```
Step 1: MINUTES.md に「#バグ #解決」エントリを追記する（§21 参照）
Step 2: 新しいパターン・教訓があれば MASTER_LESSONS.md に昇格させる
Step 3: 重大なバグ（本番影響・データ損失・再発リスク大）は、記録前にユーザーへ確認してから
        インシデント管理に記録する（§7-2 参照。無断で記録しない・記録し忘れない）
Step 4: §14 修正サイクルを完走し、§22 に従って git push する
```

## 26. コマンド優先化ルール（新ルール・手順追加時に必ず確認）

> **目的：** 「とりあえずテキスト指示」にしがちな癖を防ぎ、最も効率的な実装方法を選ぶ習慣をつける。

新しいルール・手順・チェックを追加するとき、以下の優先順位で実装方法を検討すること：

| 優先度 | 手段 | 特徴 |
|:---|:---|:---|
| ① | **hooks**（`.claude/settings.json`） | 自動実行。ユーザー操作ゼロ。最強 |
| ② | **カスタムスラッシュコマンド**（`.claude/commands/`） | 定型手順を1コマンドで実行 |
| ③ | **スクリプト**（`scripts/`） | 繰り返し処理をPythonで自動化 |
| ④ | **テキスト指示**（`.md` ファイルへの記載） | ①〜③が無理な場合・柔軟な判断が必要な場合 |

### 26-1. コマンド化しない方が良いケース

以下に該当する場合はコマンド化を見送り、テキスト指示を維持する：
- ルールの意図・背景を理解した上で状況に応じた判断が必要な場合
- 固定化すると対応漏れが起きる（状況によって手順が変わる）場合
- コマンド化のデメリットが本来の目的の達成を妨げる場合

→ 判断理由を一言添えた上でテキスト指示を維持してよい。

### 26-2. トークン最適化との連動

Claude Code の自動コンテキスト圧縮（`/compact`）に加えて以下を意識すること：
- 毎セッション繰り返し読む必要があるファイルは hooks で自動注入できないか検討する
- 毎回手動で確認させる手順はコマンド化できないか検討する
- ただし「判断の文脈」が失われるコマンド化は本末転倒 → §26-1 を適用して見送る

## 27. 忘れ防止メカニズムのセット提案義務

> **目的：** 「ルールを追加したが誰も守らない」問題を根本から防ぐ。提案だけでなく「確実に実行される仕組み」までセットで設計する。

コマンド・手順・ルールを提案・追記する際、**忘れるリスクがある場合**は必ず防止策もセットで提案すること。

### 27-1. 忘れ防止の手段（優先順）

```
手段①：Hook化（自動実行・最強）
  → .claude/settings.json の PreToolUse/UserPromptSubmit hook で自動トリガー
  → ユーザー操作ゼロ。忘れようがない。

手段②：AIによるプロアクティブなリマインド
  → AIが文脈（「今日はここまで」等）を読んで自動提案する
  → ⚠️ AIが文脈を読み誤る可能性がある（完全な保証にはならない）

手段③：TODOリスト・チェックリストへの組み込み
  → 毎回の作業TODOの末尾に固定項目として追加する
  → ⚠️ TODOを見逃すと機能しない

手段④：よく読まれるファイルへの目立つ記載
  → CLAUDE.md の起動・終了手順に太字で記載する
  → ⚠️ 読んでも実行しないケースは防げない
```

### 27-2. 提案時の推奨形式（コマンド提案の完全テンプレート）

```
【コマンド提案】
コマンド：/project:end（セッション終了時の引き継ぎ情報を一括更新）

✅ メリット：終了手順を1コマンドで完結。毎回の長い口頭指示が不要になる
⚠️ デメリット：コマンドを忘れると引き継ぎ情報が未更新のまま次セッションが始まる

【忘れ防止策】
→ 手段②：AIが作業終了の文脈（「今日はここまで」等）を検知したら自動提案する
→ 手段④：CLAUDE.md の終了手順セクションに追記して毎回目に入るようにする
※ 手段①（Hook化）が最も確実だが、UserPromptSubmitはセッション途中でも発火するため
   「終了時のみ」のトリガーとしては設計が複雑になり、現状はデメリットが上回る
```

> ⚠️ 手段①（hook化）以外を選ぶ場合、「完全な保証ではない」旨をデメリットに必ず明記すること。
> 対策に穴がある場合はその穴を隠さず、ユーザーが正確に判断できる情報を提供すること。

## 28. アーカイブ管理ルール（ファイル削除禁止）

### 28-1. 基本ルール

- 使われなくなったファイル・コンポーネント・ページは**削除しない**
- `src/_archive/` フォルダへ移動し、`src/_archive/README.md` に理由と日付を記録する

  "exclude": ["node_modules", "src/_archive"]
}
```

| ファイル名 | 移動日 | 理由 |
|:---|:---|:---|
| OldComponent.tsx | YYYY-MM-DD | ○○コンポーネントに置き換えのため |

## 30. 相互監視ルール（アプリ作成原本 ↔ ホームページ作成原本）

> **目的：** 両原本フォルダが互いの変更を把握し、有益な更新を自分のフォルダにも採用できるようにする。

### 30-1. 実行方法（セッション開始時）

```bash
python3 scripts/compare_origins.py
```

→ 前回確認以降にホームページ作成原本で更新されたファイル・コミット一覧が表示される。
→ 採用できそうな変更があれば、ユーザーへ提案する。

### 30-2. 絶対ルール

- **ホームページ作成原本フォルダは絶対に編集しない**（git log の読み取りのみ）
- 採用判断は AI が提案し、ユーザーが最終決定する
- compare_origins.py は両フォルダの git log を読み取るだけで、どちらも編集しない
- 確認日時は `/Users/sasakihayato/.origin_watch/last_check.txt`（中立地帯）に記録する

### 30-3. 動作の仕組み

```
アプリ作成原本 ── git log 読み取り（編集なし）──┐
                                               ▼
                              compare_origins.py
                         (last_check.txt を参照・更新)
                                               ▲
ホームページ作成原本 ─ git log 読み取り（編集なし）──┘

/Users/sasakihayato/.origin_watch/last_check.txt
（中立地帯。どちらの原本も所有しない。スクリプトのみが読み書き）
```

## 付録A. AIツール別 自動化差分表（⚠️ 自分が使われているAIの列だけ見る）

> **共通ルールの本体は §7〜§30 に一元管理し、AI別に複製しない。**
> AIによって違うのは「**自動でやってくれるか／自分で手を動かす必要があるか**」だけである。
> Claude Code はフック（`.claude/settings.json`）が自動実行するため、以下を**自分で行う必要はない**。
> Gemini CLI / Antigravity にはフック機構がないため、以下を**自分で実行する**必要がある。

| 作業 | Claude Code | Gemini CLI / Antigravity |
|:---|:---|:---|
| 前回の続きの表示 | `session_start.py`（SessionStart フック）が自動表示 | 起動時に `MINUTES.md` の TL;DR を自分で読む（GEMINI.md 起動手順に明記） |
| インシデント教訓の参照 | Edit/Write 前に `INCIDENT_INDEX.md`「技術スタック別クイック検索」を自動注入（PreToolUse フック） | 修正着手前に `_PRE_CHECKLIST.md`・`INCIDENT_INDEX.md` を自分で読む（CLAUDE.md STEP3と同じ手順を実施） |
| バグ調査時のプロジェクト固有確認 | プロンプト送信時に `debug_check.py`（UserPromptSubmit フック）が自動提示 | §25-2 の内容を自分で確認する |
| 重量級ファイルの全文読み抑止 | `read_guard.py`（PreToolUse:Read フック）が自動警告 | 自分で `DOCS_INDEX.md` → 索引 → 該当部分のみ読む徹底が必要 |
| セッション終了時の未記録検知 | `handoff_reminder.py`（Stop フック）が自動で促す | 「終わります」等の発言を自分で検知し、CLAUDE.md セッション終了プロトコルを自分で開始する |
| ESSENCE_INDEX 再生成・全アプリ同期 | commit するだけで post-commit フックが `build_essence_index.py`・`sync_to_apps.py` を自動実行 | commit 後に `python3 scripts/sync_to_apps.py` を自分で実行する |
| TODOリストの提示・進捗管理 | 内蔵の **TodoWrite** で作業中の進捗を管理できる（§19-1-4 の `TODO.md`/`MINUTES.md` への永続記録は別物・代替不可） | チェックボックス付きTODOを自分で提示・更新する（§19-1-4 の形式に従う） |
| 長い会話のコンテキスト管理 | 自動要約あり（`/compact` は任意実行） | 適宜自分で `MINUTES.md` を更新し引き継ぎを行う |
| 変更前のコード退避・巻き戻し | チェックポイントが変更前に自動保存。`Esc` 2回 or `/rewind` で復元（手動バックアップ不要） | 巻き戻し機構がないため、大きな変更前に `git commit` で退避する |
| 計画の提示と承認 | プランモードで計画→承認のフローが取れる（§19-1 Pフェーズの実現手段の一つ） | 手動でTODOを提示し承認を得る（§19-1-4） |
| 並列実行（サブエージェント） | Explore／Plan／general-purpose が標準実装。**ユーザーが明示依頼した時のみ起動**（無断起動はトークン増＋auto memory非継承によるコンテキスト分断を招くため禁止。詳細は `SERVICE_ORG_CORE.md`「サブエージェントPDCAアーキテクチャ」の注記） | 同等機構なし。1コンテキストで順に処理する |
| コードレビュー | `/code-review`・`/security-review`・`/simplify` を実行（§20-2 コマンド早見表） | 内蔵コマンドなし。§19-5 全体再確認パスの項目を自分で確認する |
| 学習内容の自動記憶 | auto memory が既定ON。**ただしマシンローカルで共有されない**（下記の注意を必ず読む） | 機構なし |

> ⚠️ **auto memory を「記録」の代わりにしないこと（重要）。**
> Claude Code の auto memory（`~/.claude/projects/<project>/memory/`）は既定で有効だが、
> **マシンローカルで git 同期されず、Gemini からも他の端末からも読めない**（公式仕様）。
> したがって **MINUTES.md（§21）・MASTER_LESSONS.md・TODO/手順書系ファイルが引き継ぎの唯一の正**である。
> 「記憶したから書かなくてよい」は禁止。auto memory はあくまで個人的な作業効率の補助として扱う。

> **共通の絶対条件（AIを問わず）：** `MINUTES.md` の TL;DR と TODO の進捗が常に最新であること。
> 誰がどのAI・どのプロジェクトから見ても続きが分かる状態を保つのが、この仕組みの唯一の目的である。
