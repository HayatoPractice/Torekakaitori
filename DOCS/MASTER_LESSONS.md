<lesson_entry id="ML-008" category="開発フロー">
【ML-008】本番・JS・mainブランチを直接触らない「隔離された実験室」開発の鉄則

登録日：2026-05-29
種別：設計パターン
参照元：全プロジェクト共通知見 / 技術：Git全般・WordPress・CI/CD

■ 教訓：
「本尊（本番環境・既存のJS・mainブランチ）は絶対に直接触らない・汚さない」
必ず「隔離された安全な実験室」を作り、そこで気が済むまでテストする。
完璧になった差分だけをボタン一つで安全に本番へ上書き（マージ）する。

■ 実験室の作り方（Git）:
<good_pattern>
# 実験室を作って切り替える
git checkout -b feature/xxx

# 実装・テストが完了したら本番へ送る
git push origin feature/xxx
# → GitHub でプルリクエスト → マージ → 本番に反映

# 手元を最新に同期
git checkout main && git pull
</good_pattern>

■ WordPressでの対応：ステージング環境（本番の完全クローンURL）でテストしてから本番に上書き反映

■ 再発防止策：
「今からmainに直接コミットしようとしていないか？」を常に確認する。
Gitは「誰がmainに直接書き込んだか」を100%記録として残す。

■ 適用できる場面：全フェーズ・全プロジェクト。習慣にする。
</lesson_entry>

<lesson_entry id="ML-009" category="UI実装">
【ML-009】HTML/CSS修正時にJSのクラス名・変数名を変えると動作が壊れる

登録日：2026-05-29
種別：ミス防止
参照元：全プロジェクト共通知見 / 技術：HTML/CSS/JavaScript

■ 教訓：
AIがHTML/CSSを修正する際、JSが参照しているクラス名（querySelector等）を
変えてしまうとJSの動作が壊れる。JSのロジックは「本尊」として守る。

■ 具体例（Few-Shot）:
<bad_pattern>
<!-- AIがHTML修正時に変えた例 -->
<button class="submit-btn">送信</button>  ← クラス名を変えた

// JSは古い名前で参照しているため動作しない
document.querySelector('.btn-submit').addEventListener('click', ...)
理由：AIがデザイン的に「submit-btn → btn-submit」と変更したが、
     JS側は古い名前のまま → クリックが反応しなくなる
</bad_pattern>

<good_pattern>
<!-- JSが参照するクラスには js- プレフィックスをつけて保護する -->
<button class="submit-btn js-submit-btn">送信</button>

// JSは js- プレフィックスのクラスだけを参照
document.querySelector('.js-submit-btn').addEventListener('click', ...)
効果：AIへ「js-で始まるクラス名は絶対に変更しないこと」と命令すれば
     デザイン変更とJS動作の保護を両立できる
</good_pattern>

■ AIへの命令テンプレート：
「HTML/CSSを修正してください。ただし js- で始まるクラス名は絶対に変更しないこと。
 もしクラス名の変更が必要な場合は、JSのコードも同時に修正すること。」

■ 万が一クラス名が変わった場合の対処：JSの都合に合わせてHTMLを直す（JSは守る）

■ 適用できる場面：AIにHTML/CSS修正を依頼する全ての場面
</lesson_entry>

<lesson_entry id="ML-010" category="開発環境・自動検証">
【ML-010】自動テストはPlaywright + GitHub Actionsで本番反映前に必ず通す

登録日：2026-05-29
種別：設計パターン
参照元：全プロジェクト共通知見 / 技術：Playwright・GitHub Actions・CI/CD

■ 教訓：
コードを本番に反映する前に、Playwright（ブラウザ自動操作）で
「実際にクリックして動くか」を自動確認するパイプラインを作っておく。
GitHub Actionsでpush時に自動実行すれば人間がテストしなくてよくなる。

■ 基本的な考え方:
<good_pattern>
# テストが落ちたら絶対にマージできない仕組みを作る
GitHub Actions（ロボット）が git push のたびに自動実行：
  1. Playwrightで「ボタンをクリック → 正しい画面が出るか」を確認
  2. 全テストが通れば → マージOK
  3. 1つでも失敗したら → マージをブロック（本番に壊れたコードが入らない）
</good_pattern>

■ コスト：Playwrightは完全無料。GitHub Actionsは月2,000分の無料枠あり。

■ 素人でもできる代案（自動化が難しい場合）：
  → Claude Codeに「手元でテストして落ちたら自動で直して」と丸投げ
  → AutifyなどノーコードテストツールでPlaywrightを使わずにE2Eテスト

■ テストファイル配置：
  e2e/[機能名].spec.ts（Playwright E2Eテスト）
  src/tests/[対象].test.ts（Vitestユニットテスト）

■ 適用できる場面：本番公開するWebアプリ・フォーム・認証機能を持つ全プロジェクト
</lesson_entry>

【ML-001】@ai-sdk/google v3: googleToolsは内部パッケージからインポートする

登録日：2026-05-17
種別：ミス防止
参照元：SNS運用プロジェクト / 技術：@ai-sdk/google v3.0.72

■ 教訓：`googleTools` は `@ai-sdk/google` からはエクスポートされていない。必ず `@ai-sdk/google/internal` からインポートする。

■ Before（NG）：
  import { google, googleTools } from "@ai-sdk/google";

■ After（OK）：
  import { google } from "@ai-sdk/google";
  import { googleTools } from "@ai-sdk/google/internal";

■ 再発防止策：新規プロジェクトでai-sdk/googleを使う際は必ずバージョンを確認し、
  v3以降は内部パッケージからのインポートに変更する。
  REQUIREMENTS_LOG.mdのバージョンロック欄に記録すること。
</lesson_entry>

<lesson_entry id="ML-006" category="UI実装">
【ML-006】モーダルクローズ関数がグローバル変数を副作用でnull化する場合、使用前にローカル変数へ退避せよ

登録日：2026-05-22
種別：ミス防止

■ 具体例（Few-Shot）:
<bad_pattern>

  if (!activeDeleteReservationId) return;

  await GasClient.deleteReservation(activeDeleteReservationId); // null を渡してしまう

</bad_pattern>

async function executeDeleteReservation() {
  if (!activeDeleteReservationId) return;
  const idToDelete = activeDeleteReservationId; // ← クローズ前にローカル変数へ退避
  toggleDeleteModal(false);                     // ← ここでグローバルがnullになっても問題なし
  await GasClient.deleteReservation(idToDelete); // ローカル変数を使用
}
効果：クローズ関数の副作用に関わらず、正しいIDでDB操作が実行される。
</good_pattern>

■ 再発防止策 / 使い方：
「モーダルを閉じる関数を呼ぶ前に、その関数が副作用で何かをnull/クリアするか確認する」

■ 適用できる場面：

<lesson_entry id="ML-007" category="UI実装・非同期">
【ML-007】複数の非同期処理が並走するUIのローディング管理はboolean方式でなくcounter方式を使え

登録日：2026-05-22
種別：設計パターン
参照元：LL-003 / 発生PJ：KYGNUS予約管理 / 技術：Vanilla JS

■ 教訓：
ローディングスピナーをboolean（true/false）で制御すると、複数の非同期処理が並走した場合に
先に終わった処理がスピナーを消してしまう。カウンター方式を使えばこの競合が起きない。

■ 具体例（Few-Shot）:
<bad_pattern>
let isLoading = false;
function showLoading(show) {
  isLoading = show;
  loader.classList.toggle('hidden', !show);
}
// 処理AとBが並走すると、Aが終わった時点でBの途中でもスピナーが消える
理由：boolean方式は「最後に呼ばれた値」で状態が上書きされる。
</bad_pattern>

<good_pattern>
let _loadingCount = 0;
function showLoading(show) {
  if (show) {
    _loadingCount++;
    loader.classList.add('opacity-100');
    loader.classList.remove('pointer-events-none');
  } else {
    _loadingCount = Math.max(0, _loadingCount - 1);
    if (_loadingCount === 0) {
      loader.classList.remove('opacity-100');
      loader.classList.add('pointer-events-none');
    }
  }
}
// 全ての非同期処理が完了して初めてスピナーが消える
効果：A・Bが並走してもカウントが0になった時だけスピナーが非表示になる。
</good_pattern>

■ 再発防止策 / 使い方：
「このローディング中に別のローディング操作が発生し得るか？」を実装前に確認し、
Yes の場合はカウンター方式を採用する。

■ 適用できる場面：
カレンダー・リスト・フォームなど複数のAPI呼び出しが並走する可能性がある全てのUI。
showLoading関数を持つ全プロジェクトに適用推奨。

</lesson_entry>

■ タイトル：Enterで送信する入力欄は、必ずIMEの「変換確定Enter」を除外する

■ 症状：
日本語を入力し、スペースで変換した未確定状態（下線付き・範囲選択されたような表示）で
Enterを押すと、**確定のつもりのEnterが「送信」として扱われ、変換途中の文字列が送信される**。

■ 原因：
日本語入力(IME)では、変換確定のEnterも通常のEnterと同じ `key === "Enter"` として飛んでくる。
「今まさに変換中か」を判定しないと、確定操作を送信操作と誤認する。

■ 対策（Before / After）：
```tsx
// Before（誤り）— 日本語入力で必ず壊れる
onKeyDown={(e) => {
  if (e.key === "Enter" && !e.shiftKey) { e.preventDefault(); send(); }
}}

// After（正しい）
onKeyDown={(e) => {
  if (isImeComposing(e)) return;   // 変換中は何もしない
  if (e.key === "Enter" && !e.shiftKey) { e.preventDefault(); send(); }
}}

// 判定は1か所に共通化して使い回す（片方だけ実装する事故を防ぐ）
export function isImeComposing(e: React.KeyboardEvent): boolean {
  const n = e.nativeEvent as unknown as { isComposing?: boolean; keyCode?: number };
  return n?.isComposing === true || n?.keyCode === 229; // 229は保険
}
```

■ 重要な注意点：
1. **英語入力だけのテストでは絶対に再現しない。** 必ず日本語で動作確認すること。
2. **影響範囲は1か所ではない。** Enter送信している箇所を全部洗い出して一括で直す。
   実例では5か所すべてが同じ問題を抱えていた。
   確認：`grep -rn 'key === "Enter"' src/` と `grep -rn "isComposing" src/`
3. 日本語を扱う全アプリに共通する問題。新規に入力欄を作るたびにセットで実装する。

コードは正常なのに、ヘッドレスブラウザ（puppeteer等）の自動検証が失敗・誤検知する。

**再実行で通れば環境要因。毎回同じ箇所で落ちればアプリ側の問題。**

■ よくあるパターンと対処：
| 症状 | 原因 | 対処 |
|---|---|---|
| `Navigating frame was detached` | ブラウザの一時的な切断。失敗箇所が毎回変わる | 残留プロセスを落として再実行 |

1. 検証スクリプトは必ず `try { ... } finally { await browser.close(); }` で閉じる

2. 起動前に古いブラウザプロセスを落とす
3. **開発サーバ起動中に `npm run build` を実行しない**
4. UI比較には「CSSが適用されているか」の健全性チェックを入れる
   （`document.styleSheets.length === 0` なら中断する）
5. 検証で作られた匿名IDが本番DBに溜まる点にも注意し、定期的に掃除する

<lesson_entry id="ML-SCHEMA-001" category="DB設計・リファクタリング" priority="high">
■ タイトル：テーブルを消しても「初期構築SQL」に定義が残り、DB再構築で復活する

■ 症状：
機能整理で不要になったテーブルをDBから削除し、コード・型・ドキュメントも整理して

■ なぜ気づけないか：
既存DBは正しい状態なので、**動作テストでは絶対に検出できない**。
表面化するのは環境移行・障害復旧という、最も余裕がない場面だけ。
さらに `grep --include='*.ts'` のようなコード限定検索からSQLファイルは漏れる。

■ 対処（Before / After）：
```bash
# Before：コードだけ検索して「残骸なし」と判断する
grep -rn "gemini_questions" --include='*.ts' --include='*.tsx' .

# After：拡張子を限定せず、SQL・ドキュメント・設定まで含めて検索する
grep -rn "gemini_questions" --include='*.ts' --include='*.tsx' \
     --include='*.sql' --include='*.json' --include='*.md' . | grep -v node_modules
```

■ 重要：初期構築SQLを「丸ごと削除」してはいけない
アプリが起動時に自動作成するテーブルと、このSQLでしか作られないテーブルが
混在していることがある。実例では10テーブル中4つがSQLファイル専属で、
消していたらDBを作り直せなくなっていた。**先に「どのテーブルを誰が作るか」を確認する**。

■ 修正後は2方向で実測する（推測で終わらせない）：
1. **既存DBへの無害性**：ファイル全体を実行し、実行前後で列・索引・テーブル・データ件数を
   丸ごと比較して完全一致を確認する（`IF NOT EXISTS` 付きでも実際に流して確かめる）
2. **新規構築の正しさ**：隔離した検証用スキーマに流し、本番と列レベルで一致するか確認する
```sql
CREATE SCHEMA verify_fresh;   -- テーブル名を verify_fresh.xxx に置換して実行
-- 本番スキーマと列を比較 → DROP SCHEMA verify_fresh CASCADE;
```
本番を汚さずに「まっさらから作れるか」を試せるため、他の場面でも応用が利く。

■ 同時に確認すべき残骸（実例で全て見つかった）：
初期構築SQL / READMEの「実装済み[x]」 / セットアップ手順書のテーブル一覧 /
型定義（33型中22型が未使用だった） / 到達不能な分岐 / `ensureXxxSchema()`

<lesson_entry id="ML-LONGJOB-001" category="設計・バックグラウンド処理" priority="critical">
■ タイトル：時間のかかる処理は「必ず途中で切られる」前提で作る（切られると成果が0件と誤報告される）

■ 症状：
「100件作って」と指示 → 画面に**「0件追加しました」と成功扱いで表示**。
しかしDBを見ると**65件は実際に追加されていた**。データではなく表示が嘘をついていた。

■ 原因（3つ重なる）：
1. **実行時間の上限**：1回のリクエストで粘る設計だった。サーバーレスには上限がある
   （Vercel Hobbyは60秒。`maxDuration = 300` と書いてもプランの上限は超えられない）。
   259秒動いた末に応答ごと切られ、最後の「完了」イベントが届かなかった。
2. **完了イベントだけで数えていた**：届かないと初期値0のまま、しかも未完了フラグも立たず成功表示。
   サーバーは1件ごとに保存イベントを送っていたのに、受け手が捨てていた。
3. **生成物の32%が既存データと重複**：AIに「既にあるもの」を伝えていなかった。

■ 対処（Before / After）：
```ts
// Before：完了イベントだけに頼る → 切れたら 0 のまま「成功」表示
let doneCount = 0;
if (evt.type === "done") doneCount = evt.count ?? 0;
setLastResult({ added: doneCount, incomplete });

// After：1件ごとの保存イベントを数え、完了は「あれば使う」程度に留める
if (evt.type === "saved") savedSeen++;
if (evt.type === "done")  doneCount = evt.count ?? 0;
return { added: doneCount ?? savedSeen, gotDone: doneCount !== null };
// 完了が来なければ「未完了」として実数を添えて報告する
```

■ 設計の型（そのまま流用できる）：
- サーバー：1回を**上限の8割以下**（60秒上限なら50秒）で切り上げ、その回の成果を返す
- クライアント：目標に届くまでチャンクを繰り返し、成果を**通しで積み上げる**
- **待機はサーバー側でやらない**。関数内 `sleep` は実行時間を食い潰し、待った末に切られる。
  レート制限の回復待ちは、時間制限のないクライアント側で行う
- 歯止め：回数上限・全体時間上限・**「前回より残りが減っていなければ打ち切る」**

■ 併発しやすい罠：
**分割方式にしたのに「続きを呼ぶ」を実装し忘れる。** 同じアプリ内の別APIで実際に起きており、
「22件処理・残り40件」で止まったまま放置されていた。分割と再開は必ずセットで実装する。

■ 切り分けの決め手：
**外部API呼び出しの成否・エラー種別・所要時間をログに残しておくこと。**
「AI呼び出しは95回成功」と分かった瞬間に、原因を生成側ではなく保存・集計・表示側へ絞り込めた。
これが無ければ切り分け不能だった。

■ 出典：INC-012（英会話学習アプリ / 2026-08-10。単語100件の一括生成）
</lesson_entry>

<lesson_entry id="ML-NEON-001" category="API連携・DB" priority="critical">
■ タイトル：HTTPベースのDBドライバは、フレームワークのfetchキャッシュに載って永久に古い値を返す

■ 症状：
DBには正しいデータが入っているのに、APIが常に同じ（古い）結果を返す。

■ 原因：
Neon serverless などのHTTPベースのドライバは内部で `fetch` を使う。

```ts
// After：キャッシュを明示的に無効化する
export const sql = neon(DATABASE_URL, { fetchOptions: { cache: 'no-store' } });
```

■ 切り分けの決め手：
「更新したのに画面が変わらない」ときは、**DBを直接見て実データと画面を突き合わせる**。
実データが正しいのに画面が古いなら、原因はロジックではなく取得経路（キャッシュ）にある。

■ 併発しやすい罠：
引数なしのGET APIがビルド時に静的化され、同じ結果を返し続ける。
`export const dynamic = 'force-dynamic'` で防ぐ。

ポップアップ本体は**不透明**にする（半透明は背後の色が混ざりコントラストが読めない）。

■ 繰り返さないために：
1箇所直して終わりにしない。**同じ書き方を全ファイル横断で探す**。
```bash
grep -rn "bg-primary\|from-primary" --include='*.tsx' src | grep "text-white"
```
実際、3回目の修正時にこれを実行して未修正の5箇所を一度に発見した。

■ 検出：両テーマでコントラスト比を機械的に測る。
背景をたどる際は `background-image`（グラデーション）も見ること（見落とすと誤報告が出る）。

■ 出典：INC-016（英会話学習アプリ / 2026-08-09〜11、3回発生）

<lesson_entry id="ML-INVARIANT-001" category="設計・データ整合性" priority="critical">
■ タイトル：機能のルールは「頼み方」でなく「機能」に属する — 全経路が通る場所でコードとして守る

■ 症状：
同じデータに5つの入口があり、「重複を作らない」は全経路で守られていたが、
「和訳を必ず付ける」は**どの経路でも検証していなかった**。

■ なぜ差が出たか（ここが要点）：
重複が守れていたのは、**DB制約という「どの経路も必ず通る場所」で止めていたから**。
和訳は「AIが付けてくれるはず」というプロンプト頼みで、関所がどこにも無かった。

■ 対処（Before / After）：
```ts
// Before：入口ごとに書く（新しい経路が増えるたび漏れる）＋AIにお願いする
// After：1ファイルに集約し、全経路をそこに通す
export function checkNewVocab(input) {
  const v = normalize(input);
  if (!v.word)    return { ok: false, reason: "英語が空です" };
  if (!v.meaning) return { ok: false, reason: "和訳がありません" };
  return { ok: true, value: v };
}
```

■ 設計の型：
- 守るべき前提（不変条件）＝**コードで保証**。利用者の自由設定でも破れない構造にする
- 変えてよい好み＝**設定として外に出す**。プロンプトは「前提 → 好み」の順で組む
- 例外にする経路（復元など）は**理由をコードに明示**する。
  復元で厳しく弾くと、戻したはずの既存データが消える

■ 応用：**すでに守れているルールの「守り方」を調べ、同じ仕組みを他へ広げる**。

■ 出典：INC-019（英会話学習アプリ / 2026-08-11）
</lesson_entry>


<lesson_entry id="ML-NARROW-UI-001" category="UI設計・レスポンシブ" priority="high">
■ タイトル：狭い画面は「分割」ではなく「重ねる」／症状だけで方式を変えると別の前提を壊す

■ 症状：
「アプリを見ながらAIに相談できる」ことを狙い、スマホで画面を上下に分けた。
PCでは機能したが、スマホでは窮屈で実質使えなかった。

■ 実測（iPhone 14 / 一覧を表示した状態）：
| 状態 | 一覧に見える件数 |
|---|---|
| パネルを閉じている | 10件 |
| **アプリを縮めて上下分割** | **0件** |
| **縮めずに重ねる** | **5件** |

■ 原因：
分割そのものではなく、**アプリ本体を「縮めて」いたこと**。
```css
html.panel-open .app-shell { height: calc(100dvh - var(--panel-h)); }  /* ← これ */
```
ページ内の固定部分（見出し・検索・絞り込み）だけで694pxあり、
縮めるとその部分で画面が埋まり、**中身が押し出されて消える**。
重ねるだけならレイアウトは保たれる。

■ もう一つの失敗（プロセスの教訓）：
「窮屈」という症状に対し、原因を測らずに方式ごと変えて全画面表示にした。
領域は広がったが、**「アプリを見ながら相談する」という当初の前提そのものが失われた**。
測り直すと原因は「縮めていたこと」で、分割をやめる必要は無かった。

■ 対処の型：
- PCは縮めて共存、スマホは重ねる（メディアクエリで分ける）
- 高さは3段階：最小（見出しのみ）／通常（既定）／**入力中は全画面**
  キーボードは画面の約45%を占めるため、通常の高さでは会話が見えなくなる
- 単位は `vh` ではなく **`dvh`**（`100vh` はキーボード表示時に入力欄が裏に隠れる）

■ 判断の指針：
**「両方見せる」は横幅がある画面でしか成立しない。**
そして**症状から直接方式を変えない**。方式を変える前に
「この方式が満たしていた前提は何か」を書き出す。失われるなら解決ではなく問題の移動である。

■ 出典：INC-020（英会話学習アプリ / 2026-08-10）
</lesson_entry>

<lesson_entry id="ML-SHELL-001" category="UI設計・レイアウト" priority="high">
■ タイトル：共通シェルを持つ画面に「重ねて」出すな。ページの中身を差し替える

■ 症状：
問題集の画面を全画面オーバーレイで出したところ、
アプリ共通のヘッダー（上）と下部ナビ（下）がその上に残り、
**見出しと閉じるボタンが隠れて、その画面から出られなくなった**。

```tsx
<div className="fixed inset-0 z-50 bg-background overflow-y-auto">  // ← 覆えていない
```

■ 原因：
共通シェルはページの外側で、より大きな z-index で固定されている。
ページの中で z-index を上げても勝てない。

そして**上げれば解決する話でもない**。
シェルより上にすればナビが押せなくなり、
画面幅でシェルの構成が変わる（スマホは下部ナビ／PCはサイドバー）ため、
ある幅では勝ち、別の幅では負ける状態になる。

■ 対処の型：
重ねるのをやめ、**ページの中身そのものを差し替える**。

```tsx
{quizOpen ? <Quiz ... /> : <> ...通常の一覧... </>}
```

シェルとの重なりを考える必要がなくなる。
副次的に「解いている間は答えになる一覧を出さない」という要件も同時に満たせた。

■ 見つけ方：
`innerText` では気づけない（覆われていても DOM には残るため文字列は取れる）。
**スクリーンショットを撮る**こと。

■ 判断の指針：
**z-index の取り合いになった時点で、方式が間違っている。**
共通レイアウトを持つアプリでは「重ねる」より「差し替える」が既定。

■ 出典：INC-023（英会話学習アプリ / 2026-08-17）
</lesson_entry>

<lesson_entry id="ML-DUPFETCH-001" category="パフォーマンス・React" priority="high">
■ タイトル：CSSで出し分けた部品は両方マウントされる。共通部品に通信を持たせる前に個数を数える

■ 症状：
共通ヘッダーの歯車にバッジを付けたら、**全ページで同じAPIが2回**走った。

■ 原因1：見えていないだけで、両方とも存在している
```tsx
<div className="lg:hidden">   <SettingsMenu /> </div>   {/* スマホ用 */}
<div className="hidden lg:flex"><SettingsMenu /> </div>   {/* PC用 */}
```
`hidden` は**表示を消すだけ**。要素は存在しマウントされ、`useEffect` も走る。
画面には1つしか見えないため、目視では絶対に気づけない。

■ 原因2：取得処理が、自分で更新する値を依存に持っている
```tsx
const fetch = useCallback(async () => {
  if (list.length && !target) setTarget(list[0]);   // target を更新する
}, [target]);                                        // その target に依存 → 再取得
```

■ 対処の型：
1. 複数箇所で使う値は**1か所で持って配る**（キャッシュ＋購読）。
   同時に呼ばれても実際の通信は1回にする。変化時は購読側へ通知して古い値を残さない。
2. 依存を外し、**直前の値は更新関数の引数から受け取る**：`setTarget(prev => prev || list[0])`

■ 確かめ方：
**本番ビルドで通信の回数を実際に数える。**
開発モードは StrictMode で二重に走るため判断材料にならない。

■ 判断の指針：
**共通レイアウトに置く部品に通信を持たせるときは、その部品が何個描画されるかを先に数える。**
機能を足したら「増えた通信はいくつか」を必ず実測する。

■ 出典：INC-024（英会話学習アプリ / 2026-08-17）
</lesson_entry>

<lesson_entry id="ML-AIFORM-001" category="API連携・AI活用" priority="critical">
■ タイトル：AIは「正しい指摘を違う欄に入れる」。形式の妥当性はアプリ側で検査する

■ 症状：
既存データをAIに校正させたところ、綴りの誤った単語 `accomodate` に対し、
**「意味」（日本語）の欄への修正案として `accommodate`（英単語）** を返した。

指摘の内容は正しい。しかし置き場所が違う。
そのまま採用すれば**和訳「収容する」が英単語で上書きされていた**。

■ 原因：
プロンプトで「和訳の欄には日本語を入れる」と指示しても守られないことがある。
さらに根本には設計上の抜けがあった。
**見出し語を点検対象に入れていなかった**ため、
AIは綴りの誤りを指摘したくても入れられる欄が「意味」しか無かった。
**正しい置き場所が無ければ、AIは間違った場所に入れるしかない。**

■ 対処の型：
1. **欄ごとに入り得る形を決め、食い違う候補は採用前に捨てる**
```ts
if (JAPANESE_FIELDS.has(field)) return hasJapanese(s);
if (ENGLISH_FIELDS.has(field))  return !hasJapanese(s) && hasLatin(s);
```
2. **正しい置き場所を用意する**（見出し語も点検対象に加えた → 正しい欄に出るようになった）
3. AIが返した文字列を**列名・パス・IDとしてそのまま使わない**（固定の対応表で受ける）
4. 修正案は**自動適用しない**。候補として貯め、採否は人が1件ずつ選ぶ

■ 判断の指針：
**内容の正しさは判定できなくても、形式の妥当性（言語・長さ・種別）は機械的に判定できる。**
指示で守らせることと、検査で弾くことは別物。両方やる。
AIが「正しい指摘を間違った場所に入れた」ときは、**置き場所が無いことを疑う**。

■ 出典：INC-025（英会話学習アプリ / 2026-08-17）
</lesson_entry>

<lesson_entry id="ML-BACKUP-001" category="DB設計・データ保全" priority="critical">
■ タイトル：表を1つ足したら、控え・書き出し・読み込みの3経路も同時に更新する

■ 症状：
後から追加した表が、**自動バックアップにも書き出しにも入っていなかった**。
他の表は入っていたため、バックアップ機能は動いているように見え続けていた。

■ 原因：
新しい表を追加するとき触るのは「スキーマ・API・画面」で止まる。
**保全の経路はその機能とは別の場所にあるため、視界に入らない。**
入れ忘れてもエラーは出ず、テストも通り、画面も正常に動く。
**失って初めて気づく**種類の抜けで、気づいたときには手遅れ。

危険度はあとから上がる。その表が「ついでに貯まるもの」から
中核データへ育っても、保全の抜けは放置されたままになる。

■ 対処の型：
4か所すべてに通す。1つでも欠けると復元できない。
| 経路 | 内容 |
|---|---|
| 控えを取る | SELECT を追加し payload と counts に入れる |
| 控えから戻す | INSERT を追加 |
| 書き出し | SELECT を追加し JSON に入れる |
| 読み込み | INSERT を追加 |

古い世代の控えには入っていないため、**読む側は「無い」を許容する**（`?? []` / `?? 0`）。
二重に読み込んでも増えないよう `ON CONFLICT` で受ける。

■ 確かめ方：
**往復させる。** 書き出す → 読み込む → **もう一度読み込む**（増えないか）
→ 控えを取る → 消す → **復元する**。

■ 判断の指針：
**表の追加は「スキーマ・API・画面」で終わりではない。保全の経路までが1セット。**
列の追加（お気に入り等の属性）でも同じ抜けが起きる。

■ 出典：INC-026（英会話学習アプリ / 2026-08-17）
</lesson_entry>

<lesson_entry id="ML-AUTHTEST-001" category="開発環境・自動検証" priority="critical">
■ タイトル：認証を足すと自動検証が素通りし、「中身の無い合格」を出す

■ 症状：
ログイン必須にした瞬間、自動検証は全ページでログイン画面へ転送されるようになった。

| 検証 | 起きたこと |
|---|---|
| 画面のQA（13ページ×6画面幅） | **ログイン画面を78回調べて「合格」** |
| APIの疎通確認 | 全て401/400で「異常」の山 |
| 操作チェック | 目的の要素が無く「見つからない」の山 |

**もっとも危険なのはQA**。異常が出る検証は気づけるが、
QAは何も出さずに「✅ 問題は見つかりませんでした」と表示した。
ログイン画面は単純で崩れようがないため、きれいに合格してしまう。

■ 原因：
検証は「ログインしていない訪問者」として動く。認証を入れた瞬間、
検証が見るものが**アプリ本体からログイン画面に置き換わる**。
置き換わったことは誰も教えてくれない。検証スクリプトは
「与えられたページを検査する」だけで、それが目的のページか知らない。

■ 対処の型：
検証側でセッションを作って持たせる。鍵を持つ環境でしか作れないので安全。
```js
const value = await encode({ token: { email }, secret: process.env.NEXTAUTH_SECRET });
await page.setCookie({ name: 'next-auth.session-token', value, domain, path: '/' });
```
セッションは**最初に1回だけ**作る（ページごとに作ると無駄）。
ログイン後は読み込み量が増えるため、**ブラウザを使う検証はページを使い回す**
（毎回タブを開くと落ちる）。

■ 判断の指針：
**「異常が0件」を合格の根拠にしない。検査した対象が正しいかを先に確かめる。**
最初の1ページで、目的の画面にしか無い文言を確認し、無ければ即座に中断する。

INC-010/019（測定器は誤って異常を出す）と同根だが、
こちらは**誤って正常を出す**点でより危険。

■ 出典：INC-030（英会話学習アプリ / 2026-08-17）
</lesson_entry>

<lesson_entry id="ML-BUILDDIR-001" category="開発環境・ビルド" priority="standard">
■ タイトル：開発サーバーを動かしたまま本番ビルドを実行すると、開発側が壊れる

■ 症状：
利用者がローカルで動作確認をしている最中に本番ビルドを実行したところ、
開発サーバーが 500 を返すようになった（利用者には404として見えた）。

```
Error: Cannot find module './xxxx.js'  code: 'MODULE_NOT_FOUND'
requireStack: [ '.next/server/webpack-runtime.js', ... ]
```

■ 原因：
`next dev` と `next build` は既定でどちらも `.next` を使う。
ビルドが中身を置き換え、動作中の開発サーバーが参照先を失う。
**壊れ方が「ビルドした側」でなく「動かしていた側」に出る**ため因果が結び付きにくい。

■ 対処の型：
生成物の置き場所を切り替えられるようにする。
```js
distDir: process.env.NEXT_DIST_DIR || '.next',
```
```json
"build:verify": "NEXT_DIST_DIR=.next-verify next build",
"start:verify": "NEXT_DIST_DIR=.next-verify next start"
```

■ 判断の指針：
**検証目的のビルドは本番用と別の場所へ出す。**
そして「404が出る」という報告を額面どおり受け取らない。
**実際の応答コードを自分で測る**（今回もそれで原因が500だと分かった）。

■ 出典：INC-029（英会話学習アプリ / 2026-08-17）
</lesson_entry>

<lesson_entry id="ML-SSRTIME-001" category="設計・SSR" priority="high">
■ タイトル：描画の中で「今」を計算しない。時間帯によってだけ壊れる

■ 症状：
日記ページで React のハイドレーション不一致（#425）。
描画中に「今日の日付」を直接計算しており、
サーバー（UTC）と端末（日本時間）で日付が食い違う時間帯
——**日本の0時〜9時**——だけ表示が一致しなくなる。

■ なぜ見つけにくいか：
たまたま0時台に検証したため発覚した。
**日中に検証していれば再現しない**（UTCと日本時間の日付が同じため）。
「検証が通った」ことが安心の根拠にならない類の不具合である。

■ 対処の型：
端末に依存する値は、描画後に確定させてから出す。
```tsx
const [today, setToday] = useState("");
useEffect(() => { setToday(todayKey()); }, []);
return <p>{today ? `${today} の日記` : "今日の日記"}</p>;
```

■ 判断の指針：
**サーバーとブラウザで違い得るものを、描画の中で計算しない。**
日付・時刻・乱数・端末の設定がこれに当たる。
時刻に依存する箇所は、**その時間帯を狙って検証する**か、
時刻を固定して確かめる。

■ 出典：LL-019（英会話学習アプリ / 2026-08-18）
</lesson_entry>

<lesson_entry id="ML-CTXLIMIT-001" category="AI活用・文脈" priority="standard">
■ タイトル：AIへ渡す量の上限は勘で決めず実測する。画面が増えたら見直す

■ 症状：
AIが画面の内容を読んで答える機能で、渡す量に700字の上限を置いていた。
単語帳では**10語目の途中で切れており**、「表示されている単語を全部挙げて」に
一部しか答えられない。件数を尋ねると「11件」と誤答した（実際は20件）。

**AIは切れていることを知らないので、届いた範囲で自信を持って答える。**
利用者からは「AIが間違えた」ように見え、原因にたどり着きにくい。

■ 原因：
上限を決めた当時は妥当だったが、その後に画面の情報量が増えても見直さなかった。

■ 対処の型：
全画面を実測してから決める。
| 画面 | 文字数 |
|---|---|
| 発音練習 | 2029 |
| 設定 | 1800 |
| 単語帳 | 1329 |
実測の最大より余裕を持たせた値にする（この例では2500字）。
**画面を増やしたら見直す**旨をコードに書き添えておく。

■ 判断の指針：
**上限に当たっているかは、送っている文字数を測れば分かる。**
AIの答えが不正確なとき、モデルの能力を疑う前に
「そもそも情報が届いていないのでは」を確かめる。

■ 出典：LL-020（英会話学習アプリ / 2026-08-17）
</lesson_entry>

<lesson_entry id="PE-001" category="プロンプト設計" priority="standard">
■ タイトル：構造化プロンプト（XMLタグの活用）
■ 原則：
全ての指示・データ・思考プロセスをXMLタグで囲み、AIが情報を混同しないようにする。
- `<thinking>`: 内部推論・リスク分析
- `<instructions>`: 具体的な命令
- `<example>`: Few-shot用の例示
- `<context>`: 背景情報
</lesson_entry>

<lesson_entry id="PE-002" category="プロンプト設計" priority="standard">
■ タイトル：思考プロセス（Chain-of-Thought）の標準化
■ 原則：
重大な判断・複雑な実装前に `<thinking>` タグ内で以下を検討する。
1. 前提条件の確認：何が分かっていて何が不明か
2. リスク評価：既存機能への影響・セキュリティ・パフォーマンス
3. 代替案の比較：複数アプローチを検討し最善策を選んだ理由
4. 検証計画：どうテストし成功を定義するか
</lesson_entry>

<lesson_entry id="PE-003" category="プロンプト設計" priority="standard">
■ タイトル：Few-shot / One-shot プロンプティング
■ 原則：
- One-shot：複雑なアルゴリズムや特定フォーマットが必要な場合、1つの完璧な例を提示するだけで精度が劇的に向上
- Few-shot：出力のトーンやスタイルを厳密に制御したい場合、複数の例を提示する
</lesson_entry>

<lesson_entry id="PE-004" category="プロンプト設計" priority="optional">
■ タイトル：刺激プロンプト（Stimulus Prompting）
■ 原則：
複雑な課題に対し、命令の最後に以下のような「刺激」を加えるとモデルの注意力が高まる。
例：「このセキュリティチェックを通過しない限り、リリースは許可されません」
例：「効率性を極限まで追求し、計算量を最小限に抑えてください」
</lesson_entry>

<lesson_entry id="PE-005" category="プロンプト設計" priority="standard">
■ タイトル：プロンプト自己改善ループ
■ 原則：
AIの結果が期待に沿わない場合、単にやり直すのではなく
「プロンプトのどこに誤解を招く表現があったか」を自己分析し、
プロンプト自体を修正してから再試行する。
</lesson_entry>

<lesson_entry id="PE-006" category="プロンプト設計・AI活用" priority="standard">
■ タイトル：統合的教訓（AI開発の本質3原則）
■ 原則：
1. **検証の自動化**：コードを書くだけでなく、それが「正しい」ことをAI自身がテストを通じて証明する仕組みが必須。実装と検証をセットで行うことでバグの混入を防ぐ。
2. **継続的なリファイン**：プロンプトは一度書いて終わりではなく、実証的な評価に基づいて反復的に改善し続けるべきである。結果が悪ければプロンプト自体を見直す（PE-005参照）。
3. **コンテキストの純度**：必要な情報のみを、最適なタイミングで、最適な構造で提供することがAIのパフォーマンスを決定づける。不要なファイルの全読みを避け、ピンポイント読込を徹底すること（→ DOCS_INDEX.md の2層構造設計の根拠）。
</lesson_entry>
