## CHAPTER 1｜環境別セットアップ手順
> ⏱ 所要時間の目安：初回のみ 約10〜15分

「プロジェクトフォルダに DOCSファイルを置いてAIに読み込ませる」が基本です。
環境ごとに違うのは読み込ませ方だけです。

**【必須】プロジェクト管理・トークン削減ファイル（13個）— 全環境・毎回必須**
```
⓪ .antigravityignore / .geminiignore / .aiexclude  ← 静的除外設定（ルート）
① AGENTS.md              ← AI行動規範・トークン削減指示書（ルート）
② scripts/skeletonizer.py ← コードシグネチャ抽出ユーティリティ（ルート）
③ README.md              ← 全体地図
④ PROJECT_STATE.md       ← 現在地・開発情報
⑤ SERVICE_ORG_CORE.md    ← 組織ルール・開発フロー
⑥ SERVICE_ORG_PHASE.md   ← フェーズ・チーム定義
⑦ REQUIREMENTS_LOG.md   ← 要件・技術的負債
⑧ LEARNING_LOG.md       ← 学習記録
⑨ CONTEXT_BRIDGE.md     ← セッション橋渡し
⑩ MASTER_LESSONS.md     ← 汎用教訓集
⑪ STARTUP_GUIDE.md      ← このファイル
```

**【推奨】AI強化リファレンス（4つ）— Claude Code使用時に追加**
```
⓪ MASTER_REFERENCE.md           ← AIエージェント知見
⓫ CLAUDE_CODE_GUIDE.md          ← ツール運用ガイド
⓬ PROMPT_ENGINEERING_MASTER.md  ← プロンプト技法
⓭ BIO_PIPELINE_INSIGHTS.md      ← パイプライン構築知見
```
※ ⓪〜⓭は CLAUDE.md 自動読込用。Antigravity・通常チャットでは必須の管理ファイル（ルートおよびDOCS内）だけでOK。

<a id="env-a"></a>
### 環境A｜Antigravity

> Antigravity とは：ブラウザ上で動くGoogleのAIエージェントです。
> ファイルをアップロードしてAIに読み込ませながら作業できます。

**【初回セットアップ手順】**

```
□ 1. ブラウザで Antigravity を開く
□ 2. 画面左側のファイルパネルを開く
       ※ パネルが見当たらない場合：左上のアイコンをクリックする
□ 3. 「新しいフォルダを作成」をクリックする
       フォルダ名の例：「TodoApp_APP」「ECサイト_APP」
□ 4. 作成したフォルダの中に「DOCS」フォルダを作成する
□ 5. 必須の9ファイルを DOCS フォルダにドラッグ＆ドロップする
       ※ ドラッグできない場合：「ファイルをアップロード」ボタンを使う
□ 6. 全ファイルがアップロードされたことを確認する
□ 7. チャット欄に以下をコピー＆ペーストして送信する
       ↓↓↓ここからコピー↓↓↓
       DOCSフォルダ内の全mdファイルを順番に読み込んでください。
       読み込み完了後、STARTUP_GUIDE.mdの現在地セクションを確認して
       起動報告をしてください。
       ↑↑↑ここまでコピー↑↑↑
□ 8. AIの起動報告を確認して作業を開始する
```

**【2回目以降の起動】**
→ CHAPTER 2を参照してください（所要時間：約1〜2分）

**【コードファイルを確認させたいとき】**
```
□ src/ フォルダもAntigravityにアップロードする
□ AIに「src/フォルダのコードを読み込んでください」と伝える
```

### 環境B｜VSCode + 拡張機能

> VSCode とは：プログラムを書くためのエディタ（無料）です。
> Claude や GitHub Copilot などのAI拡張機能を入れて使います。

**【初回セットアップ手順】**

```
□ 1. VSCode でプロジェクトフォルダを開く
       ※ フォルダがない場合：「フォルダを開く」→「新しいフォルダを作成」
□ 2. フォルダ直下に DOCS フォルダを作成する
       方法：左側のエクスプローラーパネルで右クリック→「新しいフォルダー」
□ 3. 必須の9ファイルを DOCS フォルダに配置する
□ 4. プロジェクトフォルダの直下（DOCSの外）に CLAUDE.md を新規作成する
       方法：エクスプローラーで右クリック→「新しいファイル」→「CLAUDE.md」
□ 5. CLAUDE.md に以下の内容をコピー＆ペーストして保存する
       ↓↓↓CLAUDE.mdの内容（最新版：アプリ作成原本/CLAUDE.md をそのままコピーすること）↓↓↓
       ※ 以下は概要。必ず原本フォルダの最新CLAUDE.mdを直接コピーして使うこと。
          古いサンプルを使うとインシデント管理参照（起動シーケンスStep 3）が欠落します。
       【コピー元】/Users/sasakihayato/アプリ作成関連/アプリ作成/アプリ作成原本/CLAUDE.md
       ↑↑↑CLAUDE.mdの内容ここまで↑↑↑
□ 6. AI拡張機能のチャットパネルを開く
□ 7. チャット欄に以下をコピー＆ペーストして送信する
       ↓↓↓ここからコピー↓↓↓
       DOCSフォルダ内の全mdファイルを読み込んで起動報告をしてください。
       ↑↑↑ここまでコピー↑↑↑
□ 8. AIの起動報告を確認して作業を開始する
```

**【コードを実装するとき】**
```
□ src/ フォルダをVSCode上に作成してコードを管理する
□ AIに実装を依頼するときはファイルパスを明示する
   例：「src/components/LoginForm.tsx を作成してください」
```

<a id="env-c"></a>
### 環境C｜Claude Code（CLI）

> Claude Code とは：ターミナル（黒い画面）から使うAIツールです。
> コードの実装・ファイル操作を自動で行える最も強力な環境です。

**【初回セットアップ手順】**

```
□ 1. ターミナルを開く
       Mac：「Finder」→「アプリケーション」→「ユーティリティ」→「ターミナル」
       Windows：スタートメニューで「PowerShell」を検索
□ 2. プロジェクトフォルダに移動する
       入力例：cd /Users/自分の名前/Projects/MyApp
□ 3. DOCSフォルダを作成する
       入力：mkdir DOCS
□ 4. 必須の9ファイルを DOCS フォルダにコピーする
       方法：Finderからドラッグ＆ドロップでも可
□ 5. 環境B（VSCode）の手順4〜5と同じ方法で CLAUDE.md を作成する
□ 6. Claude Code を起動する
       入力：claude
□ 7. 起動後のチャットに以下をコピー＆ペーストして送信する
       ↓↓↓ここからコピー↓↓↓
       DOCSフォルダのmdファイルを全て読み込んで起動報告をしてください。
       ↑↑↑ここまでコピー↑↑↑
□ 8. AIの起動報告を確認して作業を開始する
```

**【Claude Code特有の強みを活かすとき】**
```
□ 「src/以下のファイルを全て読み込んでください」と伝えると
   既存コードを自動で読み込んで文脈を把握してくれる
□ ファイルの作成・編集・削除をAIが自動で実行できる
□ コマンド実行（npm install、git commitなど）も依頼できる
   ただし本番環境への操作は社長承認後のみ
```

<a id="env-e"></a>
### 環境E｜Cowork Dispatch（現在の推奨環境）★

> Cowork とは：Claude デスクトップアプリのエージェント機能です。
> フォルダをマウントしてAIが直接ファイルを読み書きでき、
> セッションまたぎの引き継ぎも自動で行えます。現在の最推奨環境。

**【初回セットアップ手順】**

```
□ 1. Claude デスクトップアプリを起動する
□ 2. Cowork（Dispatch）モードを開く
□ 3. 「フォルダを選択」からプロジェクトフォルダをマウントする
       例：アプリ作成/プロジェクト名/
□ 4. チャット欄に以下をコピー＆ペーストして送信する
       ↓↓↓ここからコピー↓↓↓
       DOCSフォルダ内の全mdファイルを順番に読み込んでください。
       読み込み後、STARTUP_GUIDE.mdの起動報告フォーマットに従って報告してください。
       ↑↑↑ここまでコピー↑↑↑
□ 5. AIの起動報告を確認して作業を開始する
```

**【コードを実装するとき（Dispatch → Code Task の切り替え）】**

| 状況 | 使うべき手段 |
|---|---|
| ファイル読み書き・調査・設計 | **Dispatch**（現在の会話）で作業する |
| コード実装・bash実行・テスト | **Code Task**（`start_code_task`）を起動する |
| Developer/フォルダ内の実装 | **必ず Code Task** を使う（Dispatchから直接書けない） |
| 原本・設計ファイルの更新 | **Dispatch** で直接 Edit ツールを使う |

> ⚠️ セッション終了前に必ずCHAPTER 6（終了時チェックリスト）を実施すること
> ⚠️ 長いセッションは session-handover スキルを使ってCONTEXT_BRIDGEを更新すること

## CHAPTER 3｜新規プロジェクト開始チェックリスト
> ⏱ 所要時間の目安：セットアップ約15分 ＋ ヒアリング約15〜30分

```
【フォルダ準備】
□ 1. 新しいプロジェクトフォルダを作成する
      名前の例：「TodoApp_APP」「GAS_Tool_APP」
□ 2. アプリ特化版の必須の9ファイルをフォルダにコピーする
□ 3. 以下のファイルを「空欄にリセット」する
      □ PROJECT_STATE.md → 全項目を空欄にする
      □ REQUIREMENTS_LOG.md → 中身を空にする
      □ LEARNING_LOG.md → 中身を空にする
      □ CONTEXT_BRIDGE.md → 中身を空にする（AIが自動記入する）
□ 4. 以下のファイルはそのまま使う（リセット不要）
      □ README.md
      □ SERVICE_ORG_CORE.md
      □ SERVICE_ORG_PHASE.md
      □ MASTER_LESSONS.md（教訓はそのまま引き継ぐ）
      □ STARTUP_GUIDE.md（このファイル）

【AI起動・ヒアリング】
□ 5. CHAPTER 1の環境別セットアップ手順を実施する
□ 6. 起動後にAIが以下のヒアリングを開始する（自動で始まる）
      ヒアリング内容：
      □ ① 誰が使うアプリか
      □ ② そのユーザーが抱える問題・不便
      □ ③ 成功の定義（完成時にどうなっていれば良いか）
      □ ④ このアプリがない場合と比べて何が変わるか
      □ ⑤ 参考にしたいサービス・デザイン
      □ ⑥ 使いたい技術スタック（未定なら提案してもらう）
      □ ⑦ 締切や予算の目安
□ 7. AIが機能一覧をMust/Should/Couldに分けて提示する
      → 社長が確認・修正して合意する
□ 8. AIが実装計画書（目的から逆算した手順書）を自動生成する
□ 9. 計画書を確認して「OK」と伝えるとコード作成が開始される
```

## CHAPTER 4｜会話履歴が途切れた後の再開チェックリスト
> ⏱ 所要時間の目安：約3〜5分
> 最も重要なユースケース

```
【再開前の確認】
□ 1. DOCSフォルダに必須の9ファイルが全て揃っているか確認する
      特に重要：CONTEXT_BRIDGE.md（前回の状態が入っているはず）
□ 2. CONTEXT_BRIDGE.mdを自分で開いて以下を確認する
      □ 前回の最終タスク
      □ 実装ループ現在地
      □ 未解決のバグ・課題

【AI起動・コード読み込み】
□ 3. CHAPTER 2の「毎回の起動チェックリスト」を実施する
□ 4. 既存コードも読み込ませる（Claude Code使用時は自動）
      Antigravity/通常チャット：src/フォルダを添付する
      VSCode：「src/以下のコードを読み込んでください」と伝える

【確認・再開】
□ 5. AIの起動報告とCONTEXT_BRIDGEの内容が一致しているか確認する
      → 一致しない場合：
        「CONTEXT_BRIDGE.mdの[項目名]の内容と違います。
         CONTEXT_BRIDGE.mdの内容を正として再確認してください」
□ 6. 続きから作業を再開する
      A：「前回の続きから実装してください」
      B：「コードを確認してから方針を決めたい」
      C：「[箇所]をやり直したい」
```

<a id="chapter-7"></a>
## CHAPTER 7｜手順書（実装計画書）の作成ルール
> AIが実装計画書を作るときに守るべき基準

**【作成条件チェックリスト（AI必須確認事項）】**

```
□ ユーザーの最終目的（誰が・何のために使うか）を確認してから手順を組む
□ 機能を Must / Should / Could に分けて合意を取ってから手順化する
□ 手順は「なぜこの順番か」の理由を添える
□ 詰まりやすいポイントを先出しして対処法を記載する
□ 手順ごとに「完了したかどうか」の判断基準を明記する
□ 初心者でも読める言葉で書く（専門用語には説明を添える）
□ 技術スタックを提案する場合は理由と代替案も添える
□ 方向性が変わったら実装計画書全体を見直して更新する
□ 1つの手順に複数の目的を詰め込まない（1手順1目的）
```

**【実装計画書の品質チェック（社長が確認する項目）】**

```
□ 読んで次に何を実装すべきか明確にわかるか
□ 各フェーズのゴールと完了条件が書かれているか
□ 技術的に詰まりやすい箇所に対処法が書かれているか
□ Must機能だけでアプリとして最低限動くか確認できるか
```

## CHAPTER 8｜よくあるミスと対処法

**❌ AIが前回の状態を把握していない**
```
原因：CONTEXT_BRIDGE.mdが更新されていない・投入されていない
対処：
□ CONTEXT_BRIDGE.mdを単独でAIに渡して
  「この内容を読んで現在地を把握してください」と伝える
□ それでも不明な場合：PROJECT_STATE.mdのタスクボードを確認して
  手動で状況を伝える
```

**❌ AIがルールを無視してコードを書き始める**
```
原因：SERVICE_ORG_CORE.mdが正しく読み込まれていない
対処：
□ 「SERVICE_ORG_CORE.mdを再読み込みして
   現在の作業に適用すべきルールを確認してください」と伝える
```

**❌ AIが質問せずにいきなりコードを書く**
```
原因：新規作成フローの起動トリガーが認識されていない
対処：
□ 「新規プロジェクトです。SERVICE_ORG_CORE.mdの
   新規作成モードの確認フローに従って
   ヒアリングから始めてください」と明示的に伝える
```

**❌ コードが増えてきてAIの応答が遅い・途中で切れる**
```
原因：コードファイル＋管理ファイルでコンテキストが埋まっている
対処：
□ 一度に投入するファイル数を減らす
   最小構成：STARTUP_GUIDE + CONTEXT_BRIDGE + PROJECT_STATE + 作業対象コード
□ LEARNING_LOG.mdの古い記録を別ファイルに移す
□ src/フォルダは全部でなく作業対象ファイルだけ投入する
```

**❌ GASのコードにAPIキーが入ってしまった**
```
原因：GAS開発ルールが守られていない
対処：
□ 「SERVICE_ORG_CORE.mdのGAS開発ルールを確認して
   スクリプトプロパティを使う形にコードを修正してください」と伝える
□ 誤って公開したコードはすぐにAPIキーを無効化する
```

## CHAPTER 13｜トークン削減基盤とSkeletonizerの運用ガイド
> ⏱ トークン消費を最大90%削減し、高速かつ低コストでAI開発を運用するためのルール

今後のAPI課金（従量課金）やアカウント上限対策として、この原本プロジェクトには強力な「トークン削減基盤」が組み込まれています。

### 1. 静的除外フィルター（.antigravityignore）
* **機能**: `node_modules`、ビルド成果物（`dist`）、大容量の動画・画像バイナリ、秘密鍵などをAIが読み込まないように自動ブロックします。
* **運用**: `.antigravityignore`、`.geminiignore`、`.aiexclude` は常に同期して同一の内容で運用してください。

### 2. コード構造抽出（scripts/skeletonizer.py）
* **機能**: 関数の内部ロジックを削り、シグネチャ（クラス・関数定義・型定義）のみを残すことで、読み込むトークンを劇的に削減します。
* **実行コマンド**:
  ```bash
  python3 ./scripts/skeletonizer.py <対象ファイルパス>
  ```
* **対応言語**: TypeScript (.ts/.tsx), JavaScript (.js/.jsx), Python (.py), JSON (.json)

### ⚠️ スケルトン運用の「3つの鉄則」（デメリット対策）

```
🔴 【鉄則1】警告ヘッダーがあるコードの上書き禁止
    skeletonizerを通した出力の冒頭には「[WARNING: SKELETONIZED FOR CONTEXT]」という
    巨大な警告ヘッダーが自動挿入されます。このコードをベースにして生ファイルに
    そのまま上書き保存することは厳禁です。（内部ロジックが全削除されます）

🟢 【鉄則2】「調査はスケルトン、修正は生コード」の徹底
    関数の使い方や依存関係を調査する際は skeletonizer を利用し、
    対象のファイルが完全に特定され、いざ編集やデバッグを行う段階になったら、
    必ず対象の生のコードをフルで読み込み直してから実装してください。

🔵 【鉄則3】エスケープハッチの活用（正確性最優先）
    正確性はトークン節約に勝ります。バグ修正やコード書き込みなど、
    品質が最優先される局面では、AIはトークンを恐れずに生ファイルを大胆に要求してください。
```
