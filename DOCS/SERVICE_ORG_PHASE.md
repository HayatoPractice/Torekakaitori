▌フェーズ定義と移行ルール

フェーズ移行フロー：PMが完了条件を確認 → 秘書がまとめ → 社長が承認 → 次フェーズへ
フェーズ真の完了 = 社長がフェーズ移行を承認した時点（唯一の最終完了）

タイムアウトルール：
  各フェーズの目安期間の1.5倍を超えた場合
  → 秘書がブロッカー・課題のサマリを社長に提出する

フェーズまたぎタスクのルール：
  フェーズ移行時にPMが持ち越しタスクリストを作成する
  持ち越しが3件以上の場合：社長にフェーズ移行の保留を提案する

  □ アプリ名・目的・主要機能が定義済み
  □ tech_stackが決定済み（PROJECT_STATE.md「開発情報」に記入済み）
  □ 画面構成・APIエンドポイント一覧の初版が完成
  □ REQUIREMENTS_LOG.mdにREQ-001〜が登録済み
  □ 社長の承認完了

Phase 1｜MVP実装（目安：〜1ヶ月）
目標：最小限の機能で動くものを作る

完了条件：
  □ 全てのMVP機能の実装ループ（implement→verify→fix）が完了
  □ セキュリティチェックリストの全該当項目をクリア
  □ デモ実施・問題なし（demo/demo_results.mdに記録済み）
  □ 品質チェック通過（秘書が確認）
  □ 社長の承認完了

Phase 2｜改善・機能追加（目安：継続）
目標：ユーザーフィードバックを元に品質を上げる

完了条件（各サイクルごと）：
  □ 追加・修正した機能の実装ループが完了
  □ リグレッションチェック完了
  □ デモ実施・問題なし
  □ 社長の承認完了

▌チーム編成定義

全チーム共通ルール：
  秘書がチームを作成するとき → TEAMS/ACTIVE/[チーム名].md を作成する
  解散時 → TEAMS/DISBANDED/[チーム名].md に移動する（削除禁止）
  常駐チーム（秘書・PM・記録チーム）→ TEAMS/STANDING/ に格納済み・変更なし
  ※ Claude Code以外の環境ではPROJECT_STATE.mdのチーム一覧で代替管理する

チームファイルの記載フォーマット：
  # [チーム名]
  状態：[稼働中 / 待機中 / 解散済み]
  招集日：[YYYY-MM-DD]
  解散日：[YYYY-MM-DD]（解散済みの場合）
  役割：[担当範囲]
  担当ファイル（src/以下）：[パス一覧]
  現在のタスク：[タスク名 / なし]
  解散理由：[解散済みの場合のみ]

▌実装チーム定義（秘書が必要に応じて編成・解散）

【フロントエンドチーム】
  保管：TEAMS/ACTIVE/フロントエンドチーム.md（解散後→DISBANDED/）
  招集：UI実装 / コンポーネント設計 / 画面遷移実装が必要
  解散：UI実装完了・保守フェーズ移行後
  自走条件：tech_stack.frontendの範囲内の実装に限る
  成果物：
    □ 実装済みコンポーネント一覧（ファイルパス付き）
    □ デモファイル（demo/frontend_[機能名]_demo.html）
    □ セキュリティチェック済み確認

【バックエンドチーム】
  保管：TEAMS/ACTIVE/バックエンドチーム.md（解散後→DISBANDED/）
  招集：API設計 / DB設計 / サーバー処理 / 外部API連携が必要
  解散：API実装完了・保守フェーズ移行後
  自走条件：tech_stack.backend / databaseの範囲内に限る
  ⚠️ DBスキーマ変更・認証・決済は必ず社長確認後に実施
  成果物：
    □ APIエンドポイント一覧（メソッド・パス・リクエスト/レスポンス）
    □ ERDまたはテーブル定義（スキーマ変更がある場合）
    □ 新規追加した環境変数一覧（なければ「なし」）
    □ セキュリティチェック済み確認

【QA/テストチーム】
  保管：TEAMS/ACTIVE/QAチーム.md（解散後→DISBANDED/）
  招集：テスト設計 / バグ検証 / リグレッションチェックが必要
  解散：リリース完了後・テスト体制安定後
  自走条件：テスト実行・バグ記録・再現手順の整理に限る
  ⚠️ バグ修正の実装判断はフロント/バックエンドチームが行う
  成果物：
    □ バグ報告（再現手順・期待動作・実際動作・REQ-ID付記）
    □ リグレッション確認チェックリスト
    □ セキュリティテスト結果（該当する機能のみ）

【インフラ/DevOpsチーム】（随時招集・社長判断）
  保管：TEAMS/ACTIVE/インフラチーム.md（解散後→DISBANDED/）
  招集：デプロイ環境構築 / CI/CD設定 / パフォーマンス改善が必要
  解散：インフラ安定後
  ⚠️ prodへの変更は必ず社長承認後に実施。操作は社長が行う。

【実装レビューチーム】（随時招集・社長判断）
  保管：TEAMS/ACTIVE/レビューチーム.md（解散後→DISBANDED/）
  招集：コードレビュー / セキュリティ監査 / パフォーマンスレビューが必要
  解散：レビュー完了後
  ⚠️ セキュリティ監査の最終判断は専門家（人間）が行う
