## 1. AI生成感排除デザインルール

> バイブコーディング時も含め、UI を1行でも書く前に必ず適用すること。

### 1-1. UIコード作成前の必須3ステップ（省略禁止）

**Step 1 — ライブラリ選択**
`scripts/library_config.json` の `_image_guide` を参照し、プロジェクトのイメージキーワードに対応する UI ライブラリを選ぶ。
「とりあえず shadcn」「なんとなく MUI」は禁止。選んだ理由を一言添えること。

**Step 2 — カラーパレット決定**
プライマリ・セカンダリ・アクセントの最低3色を HEX で決定してからコードを書く。
- ⚠️ **ユーザーの色指定は常に最優先。**
- 🚫 ユーザー指定がない場合に限り、Tailwind のデフォルト Semantic Color（blue-500 等）をそのまま採用することを禁止。
- 「なぜこの色か」を業種・用途から言語化してから HEX で選ぶこと。

**Step 3 — フォント選択**
見出し用・本文用の2種を選ぶ。
- ⚠️ **ユーザーのフォント指定は常に最優先。**
- 🚫 ユーザー指定がない場合に限り、Inter フォント1種のみを無意識に使うことを禁止。
- Google Fonts から見出しに個性的なフォントを1つ選ぶ（選んだ理由を一言添える）。

---

### 1-2. AI生成感アンチパターン（禁止リスト）

> 禁止しているのは「思考停止でデフォルト値を使うこと」。ユーザー指定は常に優先。

| 分類 | 禁止パターン（ユーザー指定なしの場合） |
|:---|:---|
| **カラー** | 理由なく blue-500 / indigo-500 をそのまま採用 |
| **カラー** | 業種・ブランドと無関係な blue→purple グラデーションボタン |
| **カラー** | 全画面を白背景＋薄グレー区切りのみで統一 |
| **レイアウト** | ヘッダー→カード3列→CTA→フッター の定型構成をそのまま採用 |
| **コンポーネント** | `rounded-2xl` + `shadow-md` の白カードを全画面で多用 |
| **コンポーネント** | アイコンを全て有色丸背景に入れる画一的なパターン |
| **コピー** | 「革新的な」「シームレスな」「最先端の」などの汎用キャッチフレーズ |

### 1-3. AI感チェック（実装後・自己確認）

実装後に以下を自己チェックし、1つでも該当したら修正すること：
- [ ] カラーパレットがよくある青・グレー系のままになっていないか？
- [ ] UI コンポーネントの構成が「見たことある感じ」になっていないか？
- [ ] フォントに個性があるか（Inter / Roboto 一択になっていないか）？
- [ ] 「このアプリらしさ」が色・フォント・レイアウトに出ているか？

## 2. 品質バジェット数値基準（CWV 準拠）

→ ランク別の詳細目標値は `DOCS/SERVICE_ORG_CORE.md`「開発品質ルール ④ パフォーマンス基準」を参照すること。
以下は全アプリ共通の **リリース可否ライン**（ランクに関わらず下回ったらリリース禁止）。

### 2-1. Core Web Vitals（Google 品質指標）

| 指標 | 意味 | リリース不可ライン | 目標値（Aランク） |
|:---|:---|:---|:---|
| **LCP**（Largest Contentful Paint） | メインコンテンツ表示時間 | 4.0 秒超 | 2.5 秒以内 |
| **INP**（Interaction to Next Paint） | ユーザー操作への応答速度 | 500 ms 超 | 200 ms 以内 |
| **CLS**（Cumulative Layout Shift） | レイアウトのズレ | 0.25 超 | 0.1 以内 |

### 2-2. アプリ固有の基準

| 指標 | リリース不可ライン | 目標値（Aランク） |
|:---|:---|:---|
| **Lighthouse スコア** | 70 未満 | 90 以上 |
| **API レスポンス** | 1,000 ms 超 | 500 ms 以内 |
| **バンドルサイズ** | 500 KB 超 | 300 KB 以内 |

### 2-3. 計測タイミング

- verify ステップで主要画面・API エンドポイントを計測する
- リリース前に Lighthouse スコアを確認する（`npm run build` 後）
- 基準を超えた場合：`REQUIREMENTS_LOG.md` の技術的負債に記録する

### 2-4. セキュリティ最低要件

→ `DOCS/SERVICE_ORG_CORE.md`「OWASP Top 10 対策チェックリスト」を参照すること。
リリース前に OWASP A01〜A10 の全項目を確認し、Severity「High」以上の脆弱性がないことを必ず確認する。

## 3. アクセシビリティ方針（詳細）

最低限対応する項目（WCAG 2.1 Level A・全アプリ必須）：
- [ ] 画像に alt 属性を設定する
- [ ] フォームに label を紐づける
- [ ] キーボードのみで主要操作が可能である
- [ ] 色のみで情報を伝えない（文字・アイコンを併用する）

Level AA が必要な条件（以下に該当する場合は必須）：
- [ ] 公共機関・行政サービス向けアプリ
- [ ] 医療・福祉系アプリ（多様なユーザーが使う可能性がある）
- [ ] 教育系アプリ（特別支援が必要なユーザーを含む場合）
- [ ] 社長が明示的に Level AA を指定した場合

Level AA 追加対応：フォーカスリング明示・コントラスト比4.5:1以上・エラーメッセージの具体性
