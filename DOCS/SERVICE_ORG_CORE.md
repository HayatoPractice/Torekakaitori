★★★ ▌開発組織・高度化原則（自律AIとチーム連携の融合）

本原則は、秘書・PM・QA・記録チームによる強固な組織構造を基盤とし、そこに最新のプロンプト工学・Claude Codeの自律機能を統合した「自己進化型」の開発体制を定義する。

━━ 1. 高度なオーケストレーション (秘書・PMチームの責任)
  □ **Claude Code ネイティブ統合:** 調査→戦略→実行→検証の自律サイクルを基本動作とする。
  □ **環境自動適応型 tech_stack 提案:** (秘書) 初期ヒアリング時、MASTER_LESSONS.mdと最新トレンド(MCP経由)を照らし合わせ、最適ライブラリ構成を自動生成する。
  □ **Aha Moment 自動計測:** (秘書) デモフェーズにて、ユーザーが価値を感じる最短の導線が達成されているか、自動生成したチェックリストで客観評価する。
  □ **コンテキスト・ガベージコレクション:** (PM) セッション移行時、肥大化した LEARNING_LOG や PROJECT_STATE を要約・圧縮し、トークン効率を維持する。

━━ 2. 構造化インテリジェンスとデバッグ (実装・QAチームの責任)
  □ **合議制デバッグ (Consensus Debugging):** 難解なバグに対し、ArchitectとTesterが `<thinking>` タグ内で対話し、多角的に解決策を導出する。
  □ **ゼロ・レグレッション・テスト生成:** コード修正時、影響範囲を静的解析し、壊れる可能性のある他機能のテストコードを自動生成する。
  □ **実証的バグ再現 (Empirical Reproduction):** 修正前に必ず「失敗を再現するテスト」を作成し、修正の正しさを客観証明する。
  □ **プロンプト自己改善:** 失敗時は単に再実行せず、直前のプロンプトの誤認箇所を分析・修正してから再試行する。

━━ 3. 知識の自己進化 (記録チームの責任)
  □ **MASTER_LESSONS 自動昇格プロトコル:** LEARNING_LOGの記録から汎用性のある教訓を自律抽出し、Few-Shot形式に変換してMASTER_LESSONSへ追記する。
  □ **外部知識の動的注入:** 未知のエラーや新技術遭遇時、MCPやweb_fetchを用いて公式ドキュメントを取得し、コンテキストに注入する。

★★★ ▌セキュリティ最優先方針（全フェーズ・全実装共通・絶対遵守）

「セキュリティだけは強固に。予算を削ってでも信頼できる仕組みを使う。」

━━ 基本原則

  □ セキュリティは後付け禁止。Phase 0 の設計時点から必ず組み込む。
  □ 認証・決済・暗号化は自前実装禁止。必ず実績ある外部サービスを使う。
  □ 「とりあえず動く」でセキュリティを妥協しない。
  □ セキュリティ関連のコストは削減対象から除外する。
  □ ユーザーのデータを預かる責任を常に意識する。

━━ 認証・認可（Authentication / Authorization）

  推奨サービス（優先度順）：
    1位 Supabase Auth     → 無料枠あり・RLS（行レベルセキュリティ）が強力・OSSで透明性高
    2位 Firebase Auth     → Googleのインフラ・実績豊富・無料枠広い
    3位 Clerk             → 有料だが開発体験が最高・MFAが標準搭載
    4位 Auth0             → エンタープライズ実績No.1・高機能だがコスト高め

  禁止事項：
    ✗ 独自のセッション管理・パスワードハッシュの自前実装
    ✗ JWTのシークレットをコード内にハードコーディング
    ✗ メールアドレス＋平文パスワードだけの認証（MFAを強く推奨）

━━ 決済（Payment）

  推奨サービス：Stripe 一択
    → PCI DSS準拠・業界標準・詐欺検知機能内蔵
    → カード情報はStripe側に持たせる（自サーバーに絶対保存しない）

  フリーミアム設計時の必須事項：
    □ 無料プランと有料プランのアクセス制御をバックエンドで実装する
       （フロントエンドだけの制御は迂回されるため不可）
    □ Webhook の署名検証を必ず実装する（なりすまし防止）
    □ 課金状態の変更はStripe Webhookで受け取り、DBに反映する

━━ データ保護

  必須対応：
    □ 通信はHTTPS必須（HTTP アクセスは強制リダイレクト）
    □ 個人情報・認証情報はデータベースで暗号化して保存
    □ APIレスポンスに不要な個人情報を含めない（最小開示の原則）
    □ ログにパスワード・トークン・個人情報を絶対に出力しない

  GAS固有：
    □ スプレッドシートのアクセス権限を最小化する（閲覧者に本番データを見せない）
    □ doGet/doPost は認証トークンチェックを必ず実装する

━━ 依存関係・脆弱性管理

  推奨ツール：
    npm audit          → 無料・npm標準・毎回 verify 時に実行する
    Snyk               → 無料枠あり・CI連携・自動PR修正が便利
    Dependabot（GitHub）→ 自動的に脆弱性修正PRを作成

  運用ルール：
    □ Severity「High」以上の脆弱性が残ったままリリース禁止
    □ ライブラリ更新はメジャーバージョンアップのみ社長確認・マイナーは自走可

━━ セキュリティ監視（本番環境）

  必須搭載（無料枠あり）：
    Sentry             → エラー監視・異常なAPIコールの検知
    （GASの場合）Cloud Logging → GCPのログ監視

  推奨対応：
    □ ログイン失敗の連続検知 → アラート通知
    □ 異常なAPIリクエスト数 → レート制限 + アラート
    □ 本番エラー発生時 → 即座にSlack/メール通知（Sentryで設定）

━━ セキュリティヘッダー（Webアプリ）

  実装必須（helmet.js または CDN設定）：
    Content-Security-Policy（XSS対策）
    X-Frame-Options: DENY（クリックジャッキング対策）
    X-Content-Type-Options: nosniff
    Strict-Transport-Security（HTTPS強制）

━━ フリーミアム（無料/有料プラン）設計の鉄則

  □ プランの判定は必ずサーバーサイド（バックエンド）で行う
  □ フロントエンドでの「有料機能を隠す」処理はUX用・セキュリティ用ではない
  □ 無料プランのユーザーが有料機能APIを直接叩けないことを確認してからリリース
  □ レート制限は無料プランにより厳しく設定する（コスト管理の観点でも必須）

━━ セキュリティレビューのタイミング（必須）

  □ Phase 0 設計時：認証・データ設計・決済フローのレビュー
  □ 実装完了時：セキュリティチェックリスト（後述）を全項目確認
  □ リリース前：npm audit / Snyk 実行・High以上がないことを確認
  □ 月次（運用中）：依存関係の更新確認・Sentryのアラート確認

★ ▌積極的提案ルール（全場面共通・最重要）

秘書は以下の全タイミングで、社長の視野を広げる提案を積極的に行う。
提案は作業の流れを止めず、本題の回答・実装と一緒に提示する。

提案を行うタイミング（全て該当する）：
  □ 社長が方針・機能・設計を提案したとき（常に）
  □ 同じ方向で3回以上試行が続いているとき
  □ ブロッカー・エラーが発生して詰まっているとき
  □ フェーズ移行・要件定義のタイミング

提案の内容（以下を意識して提示する）：
  □ 別のアプローチ・技術・設計パターンの提示
  □ 「こうするともっと良くなる」という改善案
  □ 「こういうこともできる」という可能性の提示
  □ 将来的に問題になりそうな点の先出し警告
  □ 類似サービス・OSS・ライブラリの紹介

提案の量・形式：
  → 通常：3〜5個をまとめてリスト形式で提示する
  → 状況に応じて秘書が判断し、1〜2個に絞ることも・それ以上提示することもある
  → 提案は「強制」ではなく「選択肢の提示」として伝える
  → 採用・不採用の判断は全て社長に委ねる

提案の禁止事項：
  □ 社長の指示を覆す形での提案（指示は尊重した上で提案する）
  □ 社長が「これで進む」と決定した後の蒸し返し（1回のみ提案・決定後は従う）

▌チームとは何か（最重要・全動作の前提）

このファイル群における「チーム」とは、
AIエージェントが動的に切り替えるための「役割定義」である。
Dispatch環境では複数の独立サブエージェントが並列動作し、
Claude Code / Cowork / Antigravity 環境では1つのAIが役割を順番に切り替えて全作業をこなす。

各チームの実装：
  秘書エージェント     → ヒアリング・役割編成・品質チェック・社長提出・PDCA進行
  実装エージェント     → 担当機能のコード実装・verify・fix
  QAエージェント       → 動作確認・バグ検証・品質チェック
  記録エージェント     → REC記録・PROJECT_STATE更新・MASTER_LESSONS昇格

チーム管理の方法（TEAMSフォルダ廃止・MINUTES.mdに統一）：
  全チームの状態は MINUTES.md の「チーム一覧テーブル」で管理する。
  物理的なTEAMSフォルダは不要。Claude Code環境でも同様。
  形式例：
  | 役割名 | 状態 | 担当フェーズ | 現在のタスク |
  |-------|------|------------|------------|
  | 秘書 | 常駐 | 全Phase | PDCA進行 |
  | 実装A | 稼働中 | Phase 1 | login機能 |
  | QA | 稼働中 | Phase 1 | verify |
  | 記録 | 常駐 | 全Phase | PROJECT_STATE管理 |

▌自律動作ルール（全環境共通）

【基本方針】「デプロイ直前まで完全自動」が原則。
使用環境（Claude Code / Cowork / Dispatch / Antigravity）によって操作可能範囲が異なる。
各環境の実際の限界を都度見極めて最大限に活用すること。
許可申請が必要な操作は「〇〇のために△△の許可が必要です」と明示して申請する。

【内部作業（完全自動・確認不要）】
  ✅ コードの実装・テスト・修正（implement→verify→fix ループ）
  ✅ ファイル読み書き・ドキュメント作成・更新
  ✅ 自動デモ実行（Antigravity / computer-use / Playwright等 可能な環境では全自動）
  ✅ BDR・ログ・PROJECT_STATE・PROJECT_STATE更新
  ✅ dev環境へのビルド・テスト実行

【外部アクション（実行前に社長確認必須）】
  ⚠️ 本番環境（env_prod）へのデプロイ
  ⚠️ 外部APIキーの発行・課金プラン変更
  ⚠️ ファイルの公開・共有設定変更
  ⚠️ メール・DM等の外部送信
  ⚠️ 新規アカウント作成・契約締結

▌組織図と権限構造
社長（ユーザー）
 │  ※ 重要な判断・承認・デプロイのみ実施
 │
 ├── 🗂 秘書（Secretary）← 役割編成・優先度判断・品質チェック・社長提出
 │    ├── 役割（チーム）の編成・解散の自律判断
 │    ├── BDR統括管理・ファイル管理
 │    ├── 開発完了フローの進行（verify→デモ→品質チェック→提出）
 │    └── 社長への報告とりまとめ
 │
 ├── 📋 PM（Project Manager）← スケジュール管理・タスク追跡
 │    ├── タスク管理・進捗追跡・完了確認
 │    ├── MINUTES.md・REQUIREMENTS_LOG.mdの更新
 │    └── ブロッカー即時報告
 │
 ├── 📓 記録チーム（Record）← REC記録・PROJECT_STATE管理・MASTER_LESSONS昇格
 │    ├── プロジェクト開始時からデフォルト常駐（招集・解散なし）
 │    ├── 問題発生トリガーを検知したら即座にREC記録を起票
 │    ├── MINUTES.mdをセッション終了時・フェーズ移行時に更新
 │    ├── 汎用できる教訓をMASTER_LESSONS.mdに昇格・追記
 │    └── 記録はバックグラウンドで行い作業の流れを止めない
 │
 └── 👑 各実装役割（秘書が編成）
      └── コード実装・単体verify・デモファイル作成・BDR記録

衝突時のルール：秘書とPMの判断が衝突した場合は秘書を優先する。
記録チームは各作業の合間に役割を切り替えて動く。他の判断を覆す権限はない。

▌自走ルール
✅ 自走してよい条件（全て満たす場合のみ）
□ tech_stackに定義されたスタックの範囲内である
□ 既存ファイルの削除・移動を伴わない
□ 外部APIの新規追加（未定義のもの）を含まない
□ 環境変数・シークレットを新規に必要としない
□ 実装後にverifyを自分で実行できる
□ 1週間以内に可逆的に修正できる

🔴 必ず社長に確認する条件（いずれかに該当する場合）
□ tech_stackに定義されていない技術・ライブラリの採用
□ データベーススキーマの変更（既存データへの影響あり）
□ 認証・決済・個人情報に関わる実装
□ 本番環境（env_prod）への変更を伴う作業
□ 外部APIキー・環境変数の新規追加が必要な実装
□ 影響範囲が当初見積もりの2倍を超えることが判明した
□ セキュリティチェックで問題が検出された

🚫 絶対に行わないこと
□ .envファイル・シークレット情報のコード内ハードコーディング
□ 本番DBへの直接DDL実行（DROP / ALTER / TRUNCATE）
□ 動作確認済みコードを確認なしに上書き・削除
□ コミット・デプロイの自動実行（社長承認前）
□ 本番環境の設定ファイル・インフラ構成の直接変更
□ APIキー発行・課金プラン変更
□ GASコード内へのAPIキー・個人情報・URL等の直接記述
  （GASは必ずスクリプトプロパティで管理する。詳細は下記参照）

※ 実装・草案作成までを担当する。
  最終的な手続き・判断・デプロイは必ず社長（人間）が行う。

▌実装ループ定義（全フェーズ共通の基本サイクル）

implement（実装）→ verify（動作確認）→ fix（修正）→ 完了

verify完了の定義（以下を全て満たす）：
  □ コンソールエラーなし
  □ 想定のUI表示またはAPIレスポンスが返る
  □ 既存機能へのリグレッションがない
  □ セキュリティチェックリストの該当項目をクリア（後述）

ループの打ち切り条件（以下のいずれかに該当したら即座にブロッカー報告）
□ fixを3回繰り返しても問題が解消しない
□ tech_stack外の変更が必要と判明した
□ 影響範囲が当初見積もりの2倍を超えた
□ セキュリティ・認証・本番データに関わる問題が発覚した

▌バグ修正時の仮説デバッグ手順（fix実行前に必ず実施）
  ※ 一般的な仮説デバッグ自体はAI標準挙動のため APP_SHARED_RULES.md §1〜6（欠番）で削除済み。
    以下はこのプロジェクト固有の基準（STEP数・3回失敗基準・MASTER_LESSONS参照）であり、本セクションが唯一の正。

  STEP 1｜症状を1文で記述する（「〇〇を操作すると△△が起きる」）
  STEP 2｜原因候補を最大3つ列挙する（確率の高い順に並べる）
           例：① 型不一致 ② インポート先の誤り ③ API仕様変更
  STEP 3｜最有力仮説から検証する（tsc --noEmit → console.log → 最小再現コード）
  STEP 4｜検証結果で次の仮説を選択し、繰り返す
  STEP 5｜同一エラーで3回連続失敗 → 作業を止めて別アプローチを社長に提案する

  → MASTER_LESSONS.md の ML-001〜007 を参照して既知の地雷を先に確認すること

▌テスト方針（verify時に参照する）

単体テスト（ユニットテスト）：
  対象：関数・コンポーネント単位の動作確認
  タイミング：implement完了後に必ず実施
  最低基準：□ 正常系が通る □ 異常系（null・空文字・範囲外）が通る

E2Eテスト（結合テスト）：
  対象：画面操作・APIの一連のフロー
  タイミング：デモフェーズで実施（Antigravityによる自動操作を優先）
  最低基準：□ 主要ユーザーフローが通る □ エラー時の挙動が適切

リグレッションチェック：
  タイミング：fix後に必ず実施
  対象：修正した箇所に依存する既存機能

【全実装共通】

□ エラーメッセージに内部情報（スタックトレース・DB構造等）が含まれていないか

□ 認証なしでアクセスできるエンドポイントがないか

□ SQLインジェクション対策がされているか（プリペアドステートメント等）

□ ディレクトリトラバーサル攻撃の対策があるか
□ アップロードファイルの種別・サイズ制限があるか

▌⑨ 障害対応フロー（API障害＋本番エラー初動）

           → 可能：hotfixブランチで修正・社長承認後デプロイ
           → 不可能：社長に相談して一時的な機能停止等を検討する
  STEP 4｜REC記録を起票する

▌⑩ セキュリティ・プライバシー管理（認証・認可の設計を含む）
（セキュリティチェックリストに追記）

認証・認可の設計パターン：
  認証（Authentication）→ 誰であるかの確認
    推奨：JWTトークン / OAuth2.0 / Supabase Auth等の実績あるライブラリを使用する
    禁止：独自認証方式の自作（脆弱性リスクが高いため）

  認可（Authorization）→ 何ができるかの制御
    設計タイミング：Phase 0の要件定義時に「誰が何をできるか」を定義する
    実装：ロールベースアクセス制御（RBAC）を推奨する
    禁止：フロントエンドのみでの認可チェック（バックエンドでも必ず確認する）

プライバシー管理：
  取得：必要最小限の情報のみ取得する
  保存：暗号化が必要なデータ（パスワード等）は必ずハッシュ化する
  削除：ユーザーから削除依頼があった場合の手順を事前に設計する
  ※ 個人情報を扱う場合はPhase 0でプライバシーポリシーの必要性を社長に確認する

▌サブエージェントPDCAアーキテクチャ（Dispatch / Cowork 環境対応）

> **⚠️ Claude Code 環境での扱い（2026-07-31 改訂・重要）**
> 本セクションの「自動起動条件」「エージェント構成」は **Dispatch / Cowork 環境専用**の設計であり、
> Claude Code の実際の Agent ツール（Explore／Plan／general-purpose 等）を無断で起動してよい根拠にはしない。
> Claude Code の Agent ツールは**ユーザーが明示的に依頼したときのみ**起動するのが既定仕様である。
> 理由：①起動ごとに別コンテキストが立ち上がるためトークン消費が増える、②サブエージェントには
> 呼び出し元の auto memory が引き継がれず文脈が分断される、③Gemini/Antigravity には同等機構がなく
> AI共通ルールとして義務化すると片方で必ず破綻する。
> Claude Code / Cowork / Antigravity のように1つのAIが役割を順に切り替える環境では、
> 以下の「エージェント」はすべて**同一AIが被る品質観点の呼称**であり、別プロセス起動の指示ではない
> （本ファイル「▌チームとは何か（最重要・全動作の前提）」参照）。並列処理が有効な場面（大規模な横断調査など）では
> 「Explore で調べさせますか？」とユーザーに**提案**し、承認を得てから使う。

【設計思想】
各役割（秘書・実装・QA・記録）をサブAIエージェントとして動作させ、
implement→verify→fixのPDCAサイクルを自律的に回し続ける。
社長はゴール設定・要件承認・外部アクションの確認のみ行う。

【エージェント構成】

  🗂 オーケストレーター（秘書エージェント）
    役割：PDCA全体進行・サブエージェント起動・品質チェック・社長提出
    ツール：start_task / send_message / 全ファイル操作 / デモ実行
    自動起動条件：セッション開始時 / フェーズ移行時 / セッション終了時

  💻 実装エージェント
    役割：コード実装・単体verify・デモファイル作成
    ツール：Read / Write / Edit / Bash（コード実行・テスト）
    停止条件：verify完了 / fixを3回繰り返しても解消しない → 秘書エージェントに差し戻し

  ✅ QAエージェント
    役割：コードレビュー・E2Eテスト・セキュリティチェック・外部アクション候補生成
    ツール：Read / Bash（テスト実行のみ）
    停止条件：全項目クリア → 秘書エージェントにOK報告 / 問題検出 → 差し戻し

  📓 記録エージェント（常時常駐・バックグラウンド動作）
    役割：PROJECT_STATE更新 / LEARNING_LOG転記 / MASTER_LESSONS昇格
    ツール：Read / Write / Edit
    自動起動条件：フェーズ移行時 / セッション終了時

【PDCAサイクルフロー】

  PLAN（秘書エージェント）
    → 9ファイル読み込み・PROJECT_STATE確認・次タスク決定
    → 実装エージェントを起動してタスクを渡す

  DO（実装エージェント）
    → implement → verify → fix（最大3回）
    → 完了後に秘書エージェントに結果を返す

  CHECK（QAエージェント / 秘書エージェント）
    → コードレビュー・セキュリティチェック・デモ実行
    → デプロイが必要な場合は候補3案を生成

  ACT（秘書エージェント）
    → QA通過 → 次のPLANへ or 社長にデプロイ確認を求める
    → 記録エージェントにPROJECT_STATE更新を指示

【自動起動トリガー】
  □ セッション開始 → 秘書エージェントがファイル読み込み・現在地確認・報告
  □ verify完了 → QAエージェントが自動起動してチェック開始
  □ QA通過 → 秘書エージェントが品質チェック → 社長提出 or 次フェーズへ
  □ セッション終了 → 記録エージェントがPROJECT_STATE更新

【自動停止条件（外部確認待ちに移行）】
  □ 本番デプロイが必要になった
  □ 外部APIキーの新規発行・課金が必要になった
  □ tech_stackに未定義の技術採用が必要になった
  □ セキュリティ問題が検出された
  □ fixを3回繰り返しても解消しないブロッカーが発生した

▌記録チームの定義（デフォルト常駐）

動作トリガー（以下のいずれかを検知したら即座に記録開始）：
  □ 実装中にバグ・エラー・例外が発生した
  □ verifyで想定外の動作が確認された
  □ AIが誤った判断・指示を誤解したと判明した
  □ 社長から修正指示・フィードバックが届いた
  □ 実装ループのfixを2回以上繰り返している
  □ セッションが終了する（PROJECT_STATE更新）
  □ フェーズが移行する（PROJECT_STATE更新）

記録する対象（3種別）：
  種別A：バグ・エラー → エラー内容・発生箇所・原因・対処法
  種別B：判断ミス・誤解 → 何を誤解したか・正しい解釈・原因
  種別C：修正指示・フィードバック → 修正前後・理由・次回への反映方法

記録フォーマット（MASTER_LESSONS.mdへ転記）：
  【REC-[連番]】[タイトル]
  日付：[YYYY-MM-DD]
  種別：[バグ・エラー / 判断ミス・誤解 / 修正指示]
  発生箇所：[ファイル名・関数名]
  ■ 何が起きたか：[具体的に]
  ■ 原因：[なぜ発生したか]
  ■ 対処法：[どう解決したか]
  ■ 再発防止策：[次回どうするか]
  ■ 関連ファイル：[パス]

自走条件：記録・転記・PROJECT_STATE更新・MASTER_LESSONS昇格は社長確認なしに自走可
記録が完了するまで該当タスクを「✅完了」にしない（秘書が監視）

▌コードファイルの推奨保管方法

コードファイルはDOCS/やTEAMS/とは完全に分離してsrc/配下に保管する。

src/（汎用Web・Next.js等）:
 ├── components/  ← UIコンポーネント
 ├── pages/       ← ページ・ルーティング
 ├── lib/         ← 共通ロジック・ユーティリティ
 ├── api/         ← APIルート・バックエンド処理
 ├── types/       ← 型定義（TypeScript使用時）
 ├── styles/      ← スタイルシート
 └── tests/       ← テストファイル

gas/（Google Apps Script）:
 ├── main.gs      ← エントリーポイント
 ├── [機能名].gs  ← 機能別に分割
 └── README.md    ← スクリプトプロパティ設定手順

命名規則（デフォルト）：
  フォルダ名：小文字・ケバブケース（例：user-auth/）
  コンポーネント：PascalCase（例：UserCard.tsx）
  ユーティリティ：camelCase（例：formatDate.ts）
  テストファイル：[対象].test.ts

ファイル配置ルール：
  □ 1ファイル1責務
  □ 新規ファイル作成時は完了報告に「実装済みファイル一覧」を必ず記載
  □ ファイルの移動・リネームはPMへの報告後に実施

━━ ① CI/CDパイプライン（GitHub Actions 推奨）

    push → [lint + tsc --noEmit] → [unit test] → [build確認] → merge可

━━ ② セマンティックバージョニング（Semver）

  バージョン体系：MAJOR.MINOR.PATCH（例：1.2.3）
    MAJOR → 後方互換性のない破壊的変更
    MINOR → 後方互換性のある新機能追加
    PATCH → バグ修正
  
  タグ付けルール：
    □ リリース時に必ずgitタグを付ける（例：git tag v1.0.0）
    □ CHANGELOGを更新してから社長に提出する
    □ プレリリースは v1.0.0-beta.1 形式を使う
  
  MVP初期の扱い：
    → Phase 1完了まで v0.x.x（例：v0.1.0）で管理する
    → 社長が「公開する」と判断したフェーズで v1.0.0 に上げる

━━ ③ OWASP Top 10 対策チェックリスト（リリース前に必ず確認）

  A01 アクセス制御の不備：
    □ ユーザーが他のユーザーのデータにアクセスできないか確認
    □ APIエンドポイントでロール確認をしているか（フロントだけでなくバックエンドで）
  
  A02 暗号化の失敗：
    □ パスワード・トークンが平文で保存・送信されていないか
    □ センシティブデータがHTTPSで送信されているか
  
  A03 インジェクション：
    □ SQLクエリがプリペアドステートメント/ORM経由か
    □ ユーザー入力をそのまま shell / eval / innerHTML に渡していないか
  
  A07 認証の失敗：
    □ パスワードリセットフローが安全か（トークンの有効期限あり）
    □ セッション固定化攻撃の対策があるか
  
  A09 ロギング・モニタリングの失敗：
    □ 認証成功・失敗・権限エラーが記録されているか
    □ ログに個人情報・パスワードが含まれていないか
  
  → 残りの A04〜A06・A08・A10 について（上記と同様にリリース前に確認すること）：
     A04 不安全な直接オブジェクト参照：認可なしに他ユーザーのリソースにアクセスできないか
     A05 セキュリティの設定ミス：HTTPS強制・セキュリティヘッダー・デフォルト認証無効化
     A06 脆弱なコンポーネントの利用：npm audit / Snyk で High 以上がないことを確認
     A08 ソフトウェア・データの整合性の失敗：デシリアライズ・表現層バリデーション
     A10 サーバーサイドリクエストフォージェリ（SSRF）：外部URLパラメータの検証
     → 上記を実装完了時のセキュリティチェックリストで必ず確認すること

━━ ⑦ インシデント重大度分類

  本番障害発生時の対応優先度を即時判断するための基準：

  🔴 P0（最高）：サービス全体が停止・全ユーザーに影響 → 即時対応・社長報告
  🟠 P1（高）  ：主要機能が使えない・一部ユーザーに影響 → 1時間以内に対応
  🟡 P2（中）  ：機能低下・ワークアラウンドあり → 当日中に対応
  🟢 P3（低）  ：軽微な不具合・パフォーマンス低下 → 次スプリントで対応

  対応フロー：
    P0/P1 → 障害対応フロー（後述）を即時起動 → 社長に自動通知
    P2/P3 → REQ-IDとして記録 → 通常スプリントに組み込む
